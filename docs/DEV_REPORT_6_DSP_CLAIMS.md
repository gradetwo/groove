## 二、速度调制与时钟漂移 —— ❌ **前提已不成立**（本周期刚建成）

报告说"引擎顶层模型依然由全局单一的静态 BPM 驱动"，`tempoBpm` 只是段落元数据里的**注释**。

**事实**：`Song.tempoTrack` 是**一等字段**（`src/types/song.ts`），`set_tempo` 是**工具**（`mcp/registry.ts`），读取在 `src/data/tempoMap.ts`
（`jump` / `linear`），而**渲染器按小节从图里取时间**（`WavExporter` 调 `stepTiming`）。

**"15ms～45ms 漂移"这条尤其不成立** ✓：时间不是"按新 BPM 重置定时器"算出来的 —— 那是会产生累积漂移的做法 ✗ —— 而是**前缀和**：
`stepTiming` 把每一小节的时长**累加**成每一步的绝对起点 ✓（`tempoMap.ts`），所以**没有可漂移的项** ✓。判据也在：`tempoWorkedExample.test.ts` 断言 66→84→66
三个点的读数与"jump 落在那小节上"，而 `tempoMap.test.ts` 断言线性斜坡的**逐小节插值总和**与 `totalSeconds` **十位小数一致** ✓。

段落上**没有** `tempoBpm` 这个字段 ✗ —— 报告描述的前提本身不存在 ✓。

## 三、底鼓相位干涉 —— ✅ **方向对，数字要更正，而且我实测过**

报告：40Hz 柏林巨柱 + 35Hz 躯体 808，在 38Hz 产生 **−8 dB** 陷波。

**实测**（audio scope 探针，本周期）：

```
berlin-orphic (basePitch 42) 0.2845 · somatic-808-gravity (basePitch 36) 0.3663 · stacked 0.1787
→ 比更响的单个低 6.23 dB，38 Hz 处 −13.45 dB → 判定 cancellation
```

所以：**方向正确** ✓、**38 Hz 正确** ✓、但**预设频率是 42/36 而非 40/35** ✓、**陷波比它说的更深（−13.45 而非 −8 dB）** ✓。
更值得记的是**论证方式** ✓：两个**独立**源的功率相加满足 `√(a²+b²) ≥ max`，所以"低于更响者 6.23 dB"**不可能是电平假象**，只能是**相消干涉** ✓。

## 七、歌词与主旋律脱节 —— 🟡 **一半错，一半对（对的那一半是本周期仍未做的）**

  `validate_prosody` 读**声调与旋律走向**并报"倒字" ✓（含 3+3 变调 ✓，声调集 1 阴平 / 2 阳平 / 3 上声 / 4 去声 / 0 或 5 轻声 ✓）；

## 一、跨段落参数突变导致的爆音 —— ⚠️ **前提与模型不符，且我尚未实测**

报告说轨道的 **Gain / Filter Cutoff / Reverb Wet 在各 Section 之间是离散阶跃赋值**。

**模型里没有这些字段** ✗✓：段落可变的是 `slot`（换 clip）、`mute`、`velocityScale`、`velocityRamp`、`overrides`（力度斜坡/移调/fill）
与 `slots`（按车道的 clip 选择）✓ —— **段落级的增益/滤波/混响赋值不存在** ✓。所以"阶跃赋值"描述的是一个**尚未存在的机制** ✓。

**但一个相关的问题是真实的** ✓：**段落边界处换 clip**（不同 pattern、不同力度）是否会在缓冲区里留下台阶 ✓ —— 我**没有实测过** ✓，
渲染器里我能看到的斜坡**都是声音内部的包络**（`WavExporter` 的 `exponentialRampToValueAtTime` ✓），**没有"段落边界淡入淡出"这一层** ✓。
所以这条应当先**测**（在段落边界取样，看有没有样本级跳变 / DC 偏移 ✓），再决定要不要建 de-click ✓ —— **不测就建，等于既不知道有没有病、也不知道药有没有用** ✓。

## 六、长曲目渲染的内存峰值与脱机阻塞 —— ✅ **确认，且有算术支持；解法的第一步已落地**

报告：6 分钟 × 8 立体声轨 → Chromium 内瞬时 1.5GB 浮点缓冲，容器里易 OOM，且没有分块流式渲染。

**算术站得住** ✓：6×60 s × 48 kHz × 2 声道 × 8 轨 × 4 B = **约 1.1 GB**（加主总线与卷积缓冲约 1.5 GB ✓）。
**架构确认** ✓：渲染依附页面里的 `OfflineAudioContext` ✓，本周期读出的根因是 **`startRendering()` 没有回调** ✓（这也是"无进度"的根因 ✓）。
**已在做的解法** ✓：`mcp/render/chunks.ts` 的 `planRenderChunks` ✓（5 条判据：恰好覆盖一次 ✓、不超 64 小节上限 ✓、优先切在段落边界 ✓、长段落照切 ✓、退化情形 ✓），
接线到 `render_song` 与"分块拼接 vs 单次整曲逐样本一致"的 audio-scope 判据是**下一步** ✓，而**母带链不得逐块各跑一遍**这条风险已具名 ✓。

## 七的落地设计（判据自检，实现待做）

**要补的是生成侧** ✓：`generate_melody` 目前只有 tonic / mode / bars / form / range / seed / density ✓，**不接收歌词与声调** ✗。

**设计** ✓（关键在"判据用的是同一个函数" ✓）：

1. `generate_melody` 增加**可选** `tones?: number[]`（一音节一声调 ✓，编码与 `validate_prosody` 一致：1 阴平 / 2 阳平 / 3 上声 / 4 去声 / 0 或 5 轻声 ✓）；
2. 生成后跑一遍**修复** ✓：对每一对相邻**发声**音符 ✓，用 `prosody.ts` **导出的同一个** `expectedDirection(tone)` ✓ 判断是否"倒字" ✓（阈值同样默认 2 半音 ✓，且同样先过 3+3 变调 ✓）—— 若是 ✗，把后一个音**镜像**到允许的一侧 ✓；镜像越界时退回**同音重复** ✓（**无移动就不是倒字** ✓）；
3. 镜像会改变它与**前一个**音的区间 ✗ → 所以**前向 + 后向**交替扫描，**设上限**（例如 4 轮 ✓）；若仍未清零 ✗ → **如实报告**"仍有 N 处未能修复" ✓，**不谎称成功** ✓；
4. **加法式判据** ✓：不传 `tones` 时，输出与今天**逐字节相同** ✓✓（同 seed 同旋律 ✓）；
5. **验收判据** ✓：传入 `tones` 时，`validateProsody(tones, 生成音高)` 的 **reversals 长度为 0** ✓✓ —— 用**同一个**判定函数，所以"生成"与"校验"不可能各说各话 ✓；
6. **反例判据** ✓：不传 `tones` 时，同一 seed 仍可能产生倒字 ✓（证明修复只在这个参数存在时生效 ✓）。

**为什么值得做** ✓：第六份报告里唯一"确实没做"的一条 ✓；而它恰好是"**校验有、生成不看**"这种最容易被误认为已完成的状态 ✓ —— 补上之后，"**写歌词 → 生成旋律 → 校验**"才是一条闭环 ✓。
