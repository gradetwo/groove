# 编排 v2：Logic Pro 式的轨道界面（设计，2026-09-28）

> 业主的决定：**轨道是音频采样器的，就应该能听到**；**呈现像 Logic Pro**；**现有固定轨道编排作为 legacy 界面，只有选这种模式才打开**；**设计与开发新界面**：添加/删除轨道 ✓、多种轨道类型 ✓、轨道可分组收纳 ✓。

## 一、而这**不是重写** —— 引擎已经在了

| 已建成 | 在新模型里的位置 |
|---|---|
| `track_id: 'audio'` + `laneId` | ⭐ **音频采样器轨道** ✓ |
| 清单 → 目录 → 源优先 SFZ → **126 include** → **1676 region** → 采样 → 解码出声 | ⭐ **这条轨道的引擎** ✓（**已在 CI 里判据守住** ✓） |
| `sampleLoader` / `audioLanePlayback` / transport 接线 | **新界面下同样适用** ✓（**它们不知道界面长什么样** ✓） |
| 固定 8 槽位 / 段落编排 | ⭐ **legacy 模式的模型** ✓ |

## 二、⭐ 第一条硬性约束：**新模型必须无损读旧歌**

⭐ 旧歌是**用户已有的数据** ✓。所以：

* ⭐ **`Song` 的既有字段一个都不动** ✓（`clips` ✓ `sections` ✓ `boundaries` ✓ `bpm` ✓ `loopRange` ✓ `arrangement` ✓）；
* ⭐ **新模型是"另一层"** ✓：`ArrangementV2 { tracks: TrackV2[] }` ✓，**它引用/包裹旧歌 ✓，不替代它** ✓；
* ⭐ **旧歌 → 新模型的读法是"投影"** ✓（8 个槽位各投影成一条轨 ✓，`track_id` 变成 `type` ✓），**反向不承诺** ✓。

### ⭐ 而这条约束是**可判据**的 ✓

> **判据**：对仓库里**每一个真实 genre** ✓，**旧歌 → 投影 → 逐字段比对** ✓ —— ⭐ **投影必须保留每个音、每个段落、每个边界** ✓✓（**一个"看起来对"的转换不算** ✗）。

## 三、轨道模型（第一版）

```ts
type TrackKindV2 = "drumkit" | "instrument" | "sampler" | "fx";

interface TrackV2 {
  id: string;                       // 稳定 ✓（不是数组下标 ✗）
  kind: TrackKindV2;
  name: string;
  color?: string;
  muted?: boolean;  soloed?: boolean;
  gainDb?: number;  pan?: number;
  parentId?: string;                // ⭐ 分组收纳（Logic 的 Track Stack ✓）
  collapsed?: boolean;
  // 类型特有（判别联合 ✓，而不是"一堆可选字段" ✗）
}
```

⭐ **判别联合而不是可选字段堆** ✓ —— **因为"一条轨同时有鼓和采样器字段"是模型允许而语义不存在的状态** ✗✓。

| kind | 特有内容 | 引擎 |
|---|---|---|
| ⭐ **`sampler`** | `sample: { assetId }`、可选 SFZ 乐器引用 | ⭐ **已建成 ✓** —— **这就是"应该能听到"的那种** ✓ |
| `instrument` | 合成器预设 / 音色 | 已有合成引擎 ✓ |
| `drumkit` | 鼓组映射 | 已有 ✓ |
| `fx` | 效果总线（**返回轨 ✓**） | 已有 FX 机架 ✓ |

## 四、分组收纳 = **Track Stack**（选 A ✓）

* ⭐ **文件夹轨**：`parentId` 指向一条 `folder` 轨 ✓ hmm: **`folder` 是不是第五种 kind** ✗✓ —— ⭐ **是** ✓：**它不发声 ✓，只收纳 ✓，可整体静音/独奏 ✓** ✓；
* ⭐ **折叠只是显示状态** ✓（`collapsed` ✓）—— **折叠不能改变声音** ✗✓（**这是一个容易犯的错** ✗）。

## 五、legacy 模式从哪进 = **入口处分流**（选 A ✓）

* ⭐ **新建/打开歌时选模式** ✓：**固定轨道（legacy）** vs **自由编排（v2）** ✓；
* ⭐ **理由**：**两种是不同数据模型** ✓ → **在入口处分流比在界面里随手切换更清楚** ✓（**切换会让人以为可以来回无损往返** ✗，**而那不成立** ✓）。
* ⚠️ **而"旧歌默认进哪个界面"仍需业主确认** ✓：我倾向 **旧歌默认进 legacy** ✓（**它本来就是按那个模型做的** ✓），**并给一个"以 v2 打开（只读投影）"的入口** ✓。

## 六、开工顺序（**先做无争议的前置 ✓**）

1. ⭐ **`TrackV2` 模型 + 投影（旧歌 → v2）+ 投影判据** ✓ —— **不依赖上面任何一个未定项** ✓，**且是任何方案的前置** ✓；
2. ⭐ **音频采样器轨道在 v2 里的定义与播放** ✓（**引擎已在 ✓，差"被 v2 模型驱动"** ✓）；
3. **v2 界面的最小骨架**（轨道列表 ✓ 添加 ✓ 删除 ✓ 静音/独奏 ✓）—— **先可用，再像 Logic** ✓；
4. **Track Stack（分组/折叠）** ✓；
5. **legacy 入口分流** ✓。

⭐ **而在业主答复之前，我按上面的默认选择（②⑤ 的 A、④ 的 A、Q2 的第一版四种 + folder）开工** ✓，**并把每一步的取舍写进仓库** ✓ —— **不阻塞** ✓。

### ⭐⭐ 而"录音音频"是一条**新需求**，它比前四条都重

⭐ **它不是在模型里加一个 `kind` 就完事** ✗✓ —— **"播放采样"与"录制音频"是两条不同的链** ✓：

| | 播放采样（**已建成 ✓**） | ⭐ **录制音频**（**全新** ✗） |
|---|---|---|
| 数据流向 | 网络 → 解码 → 图 ✓ | ⭐ **麦克风 → 采集 → 落盘 ✓** |
| 需要的 API | `fetch` ✓ `decodeAudioData` ✓ | ⭐ **`getUserMedia` ✓ `MediaRecorder`/`AudioWorklet` ✓** |
| 权限 | 无 ✓ | ⭐ **麦克风权限 ✓**（**而它必须由用户手势触发 ✓**） |
| 产物 | 一个 `assetId` 引用清单 ✓ | ⭐ **一个真实音频文件 ✓** —— **存在哪？** ✗ |
| 判据 | **已出声 ✓** | ⭐ **"录进来的东西能原样放出来"** ✓ |

⚠️ **而它引出一个架构问题，我不自己决定** ✗：**录音的产物存在哪** ✓？
* **A**：**只存本地**（IndexedDB / OPFS ✓）—— ⭐ **隐私最好 ✓、无需上传 ✓**，**但换设备就没了** ✗；
* **B**：**上传到 R2** ✓ —— **跨设备 ✓**，**但要认证 ✓、要配额 ✓、是用户数据上云** ✗（**而这与"用户自备库"的边界不同** ✓）；
* ⭐ **我的倾向是 A 起步** ✓（**先把"能录、能放、能存本地"做对 ✓**），**B 作为后续可选项** ✓ —— ⚠️ **但这是涉及用户数据的决定，所以我列出来等你一句话** ✓。

⭐ **而它不阻塞第 1 步** ✓（**模型里加一个 `recorded` 来源的采样器轨道即可 ✓**，**存储后端之后接** ✓）。

## 八、⚠️ 而 CI 那 25 分钟的真相，很可能不是取法（2026-09-28，本机复现）

修完取法之后 ✓，本机跑探针得到的是这个 ✓：

```
exit=124   ← ⭐ `timeout 900` 杀的它
… 而 `REAL SOUND — 85289 frames, peak 0.09105592` 早已打印 ✓✓
```

⭐⭐ **所以:探针干完活之后不肯退出** ✗✓ —— 它 **spawn 的 vite dev server 让 Node 的事件循环活着** ✗✓ —— ⭐ **而这与 CI 里的症状完全吻合** ✓：**那一步显示 `in_progress` 25 分钟、而日志要等进程结束才可见** ✓✓。

⭐ **结论的修正** ✓：**取法的改动仍然是对的** ✓（**240 个并发请求是真实的问题 ✓**），**但它可能不是那 25 分钟的主因** ✗✓ —— ⭐ **主因更可能是"进程不退出"** ✓✓。

**所以下一件事是**：⭐ **探针退出时清理它 spawn 的 vite 进程** ✓（以及浏览器 ✓），**并让"干完就退出"成为它的性质** ✓ —— ⭐ **否则任何用它做判据的地方都会看起来像卡住** ✗。
