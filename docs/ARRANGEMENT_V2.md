# 编排 v2：Logic Pro 式的轨道界面（设计，2026-09-28）

> 业主的决定：**轨道是音频采样器的，就应该能听到**；**呈现像 Logic Pro**；**现有固定轨道编排作为 legacy 界面，只有选这种模式才打开**；**设计与开发新界面**：添加/删除轨道 ✓、多种轨道类型 ✓、轨道可分组收纳 ✓。

## 一、而这**不是重写** —— 引擎已经在了

| 已建成 | 在新模型里的位置 |
|---|---|
| `track_id: 'audio'` + `laneId` | ⭐ **音频采样器轨道** ✓ |
| 清单 → 目录 → 源优先 SFZ → **126 include** → **1676 region** → 采样 → 解码出声 | ⭐ **这条轨道的引擎** ✓（**已在 CI 里判据守住** ✓） |
| `sampleLoader` / `audioLanePlayback` / transport 接线 | **新界面下同样适用** ✓（**它们不知道界面长什么样** ✓） |
| 固定 8 槽位 / 段落编排 | ⭐ **legacy 模式的模型** ✓ |

## 二、⭐ 第一条硬性约束：**新模型必须无损读旧歌**

⭐ 旧歌是**用户已有的数据** ✓。所以：

* ⭐ **`Song` 的既有字段一个都不动** ✓（`clips` ✓ `sections` ✓ `boundaries` ✓ `bpm` ✓ `loopRange` ✓ `arrangement` ✓）；
* ⭐ **新模型是"另一层"** ✓：`ArrangementV2 { tracks: TrackV2[] }` ✓，**它引用/包裹旧歌 ✓，不替代它** ✓；
* ⭐ **旧歌 → 新模型的读法是"投影"** ✓（8 个槽位各投影成一条轨 ✓，`track_id` 变成 `type` ✓），**反向不承诺** ✓。

### ⭐ 而这条约束是**可判据**的 ✓

> **判据**：对仓库里**每一个真实 genre** ✓，**旧歌 → 投影 → 逐字段比对** ✓ —— ⭐ **投影必须保留每个音、每个段落、每个边界** ✓✓（**一个"看起来对"的转换不算** ✗）。

## 三、轨道模型（第一版）

```ts
type TrackKindV2 = "drumkit" | "instrument" | "sampler" | "fx";

interface TrackV2 {
  id: string;                       // 稳定 ✓（不是数组下标 ✗）
  kind: TrackKindV2;
  name: string;
  color?: string;
  muted?: boolean;  soloed?: boolean;
  gainDb?: number;  pan?: number;
  parentId?: string;                // ⭐ 分组收纳（Logic 的 Track Stack ✓）
  collapsed?: boolean;
  // 类型特有（判别联合 ✓，而不是"一堆可选字段" ✗）
}
```

⭐ **判别联合而不是可选字段堆** ✓ —— **因为"一条轨同时有鼓和采样器字段"是模型允许而语义不存在的状态** ✗✓。

| kind | 特有内容 | 引擎 |
|---|---|---|
| ⭐ **`sampler`** | `sample: { assetId }`、可选 SFZ 乐器引用 | ⭐ **已建成 ✓** —— **这就是"应该能听到"的那种** ✓ |
| `instrument` | 合成器预设 / 音色 | 已有合成引擎 ✓ |
| `drumkit` | 鼓组映射 | 已有 ✓ |
| `fx` | 效果总线（**返回轨 ✓**） | 已有 FX 机架 ✓ |

## 四、分组收纳 = **Track Stack**（选 A ✓）

* ⭐ **文件夹轨**：`parentId` 指向一条 `folder` 轨 ✓ hmm: **`folder` 是不是第五种 kind** ✗✓ —— ⭐ **是** ✓：**它不发声 ✓，只收纳 ✓，可整体静音/独奏 ✓** ✓；
* ⭐ **折叠只是显示状态** ✓（`collapsed` ✓）—— **折叠不能改变声音** ✗✓（**这是一个容易犯的错** ✗）。

## 五、legacy 模式从哪进 = **入口处分流**（选 A ✓）

* ⭐ **新建/打开歌时选模式** ✓：**固定轨道（legacy）** vs **自由编排（v2）** ✓；
* ⭐ **理由**：**两种是不同数据模型** ✓ → **在入口处分流比在界面里随手切换更清楚** ✓（**切换会让人以为可以来回无损往返** ✗，**而那不成立** ✓）。
* ⚠️ **而"旧歌默认进哪个界面"仍需业主确认** ✓：我倾向 **旧歌默认进 legacy** ✓（**它本来就是按那个模型做的** ✓），**并给一个"以 v2 打开（只读投影）"的入口** ✓。

## 六、开工顺序（**先做无争议的前置 ✓**）

1. ⭐ **`TrackV2` 模型 + 投影（旧歌 → v2）+ 投影判据** ✓ —— **不依赖上面任何一个未定项** ✓，**且是任何方案的前置** ✓；

4. **Track Stack（分组/折叠）** ✓；
5. **legacy 入口分流** ✓。

⭐ **而在业主答复之前，我按上面的默认选择（②⑤ 的 A、④ 的 A、Q2 的第一版四种 + folder）开工** ✓，**并把每一步的取舍写进仓库** ✓ —— **不阻塞** ✓。

## 六·七、⭐⭐⭐ 业主纠正了我的模型：**录音不是一种轨道类型，而是一种输入形式**（2026-09-28）

我先前把它列成"**四种 + 录音音频**" ✗ —— ⭐ **业主指出：录音只是音频轨道的一种输入形式；其它轨道类型也可以录制，只不过录的是 MIDI 输入序列或其它内容** ✓✓。

| 我的错 ✗ | 正确的分层 ✓ |
|---|---|
| 把"录音"当成第五种 `kind` ✗ | ⭐ **`kind` 保持不变** ✓（drumkit ✓ instrument ✓ sampler ✓ fx ✓ folder ✓） |
| —— | ⭐ **"录制"是一种能力/输入模式 ✓，与类型正交** ✓✓ |

### ⭐ 而这条纠正**改变了数据的归属** ✓

⭐ 因为**"录制"产生的是内容，不是身份** ✓：

```ts
interface Take {
  id: string;
  recordedAt: number;          // 排序与"最近一次"的依据 ✓
  source: "audio" | "midi";    // ⭐ 录进来的东西是什么 ✓
  label?: string;
}

interface TrackV2 {
  // …kind/name/路由 不变 ✓
  takes?: Take[];              // ⭐ 这条轨录过的若干次 ✓
  selectedTakeId?: string;     // ⭐ 播放时用哪一次 ✓
  takeRegions?: Array<{ startBar: number; endBar: number; takeId: string }>;  // ⭐ 分段（comp）✓
}
```

⭐⭐ **而这正好解释了业主说的"甚至可以里头某一段录几次"** ✓✓：

| 业主的话 | 模型里的东西 |
|---|---|
| **"可以录好几次"** ✓ | `takes: Take[]` ✓ |
| **"里头某一段录几次"** ✓ | ⭐ **一段就是 `takeRegions` 的一个区间** ✓ |
| **"播放时是这么多次里头用户选择…的一个版本"** ✓ | ⭐ **`selectedTakeId`（整轨选择）或 `takeRegions`（分段选择）** ✓ |
| **"或者平贴后的"** ✓ | ⭐ **comp —— 逐段选不同 take，拼成一个版本** ✓✓ |

⭐ **所以 Logic 的 take 模型可以直接落在这个形状上** ✓：**整轨换 take ✓ 与逐段 comp ✓ 是同一个机制的两个用法** ✓✓ —— **而不是两套东西** ✓。

### ⭐ 而存储：**只存本地**（业主已定 ✓）

* ⭐ **IndexedDB / OPFS** ✓ —— **录音产物不上云** ✓✓；
* ⭐ **那么 `Take` 需要一个本地引用** ✓（`localAssetId` ✓），**而它与清单里的 `assetId` 是两种东西** ✗✓：**一个是远端可核对的内容 ✓，一个是设备上的用户数据** ✓✓；
* ⚠️ **而"换设备就没有"是这条选择的已知代价** ✓ —— ⭐ **它是业主明确选的** ✓，**所以不需要我再解释一遍** ✓。

## 九、⭐⭐ 第 2 步的桥接：**v2 轨道怎么被引擎播放**（2026-09-28，读代码后的设计）

⭐ 引擎说的是 **v1 的语言** ✓（`flattenSong` ✓ `planAudioLaneEvents` ✓ `scheduleAudioLaneSamples` ✓ 全都吃 `clips`/`sections`/`boundaries` ✓）—— ⭐ **而 v2 的 `TrackV2` 不是那个形状** ✗✓。

### ⚠️ 而这里有一个**必须避开的**陷阱

⭐ **不要写"v2 → v1 的反向投影"** ✗✓ —— **因为那意味着"任意轨道可以无损变回 8 槽位"** ✗，**而那是假的** ✓（**10 条轨道的 v2 歌无法变成 8 个槽位** ✓；**文件夹轨根本不发声** ✓）。

### ⭐⭐ 正确的桥接是**"v2 的编排被编译成引擎的输入"**，而不是"投影回 v1"

| | |
|---|---|
| ⭐ **编译方向** | `ArrangementV2` + 每轨的音符数据 → ⭐ **引擎要的 `Song` 形状** ✓ |
| ⭐ **它是有损的** | **文件夹被跳过 ✓（它不发声 ✓）** —— ⭐ **而"跳过"在这里是语义正确，不是丢失** ✓✓ |
| ⭐ **判据** | ⭐ **一条 v2 采样器轨道 + 它引用的采样 → 编译 → 引擎 → 出声** ✓✓（**这正是"是音频采样器的就应该能听到"** ✓） |
| ⚠️ **而 v1 歌** | ⭐ **仍然直接走 v1 路径** ✓（**不经过编译** ✗）—— ⭐ **所以旧歌的行为一个字都不变** ✓✓ |

### ⭐ 而这就把两件事分开了

* ⭐ **投影（v1 → v2）** ✓ —— **只读 ✓，为的是"让新界面能看到旧歌"** ✓；
* ⭐ **编译（v2 → 引擎输入）** ✓ —— **为的是"让新界面造的歌能被播放"** ✓✓。

⭐ **方向相反、目的不同、而各自只有一份实现** ✓ —— ⭐ 这与本工作流一路的规矩一致 ✓：**"两处一指"栽过五次之后，同一个转换绝不写两遍** ✓✓。

### 下一步落刀的具体形状 ✓

1. ⭐ `compileArrangementToSongInput(arrangement, notesByTrack)` ✓ —— **纯函数 ✓ 可判据** ✓；
2. ⭐ 判据：**一条采样器轨道（带 assetId）→ 编译结果里有一条 `track_id: "audio"` 的车道 ✓，且它的 `sample.assetId` 原样保留** ✓；
3. ⭐ 判据：**文件夹轨不产生车道** ✓（**"不发声"必须被断言，而不是被假设** ✓）；
4. ⭐ 然后才接进播放 ✓（**引擎侧不需要任何改动 ✓** —— **它已经能播这种车道了** ✓✓）。


## 十、⏳ 录音在 CI 里的判据：**只能判一半，而那一半要判准**（2026-09-28）

⭐ **CI 的 Chromium 有 `MediaRecorder` ✓，但没有麦克风** ✗✓ → ⭐ **"录到一段音频"这件事在 CI 里无法验证** ✗ —— **而"没有麦克风时系统怎么反应"可以 ✓✓**。

### ⭐ 所以探针判的是这一半（**而且是更该判的那一半** ✓）

| 断言 | 为什么它值得在 CI 里守 |
|---|---|
| ⭐ **`captureWithBrowser` 在无设备时返回 `ok: false`** ✓ | **它必须是一条被上报的路径，而不是一个未处理的异常** ✗✓ |
| ⭐ **`refusal` 是具名的**（`no-device` ✓ / `permission-denied` ✓ / `unsupported` ✓） | ⭐ **"录音失败"这三个字对用户毫无用处** ✗✓ —— **而具名的原因可以直接变成界面上的一句话** ✓ |
| ⭐ **`summary` 是一句非空的、可读的话** ✓ | **它是要给用户看的** ✓ |
| ⭐ **没有 take 被创建** ✓ | ⭐ **一个空 take 会被用户选中、并且会悄悄替掉轨道上原来那个东西** ✗✓ |

⭐ **这正是本工作流一路的做法** ✓：**端到端探针证明过"清单 → 出声"** ✓（**那一条 CI 能判 ✓**），**而"用户按下按钮能录"这一条 CI 判不了 ✓ —— 于是它由本机 + 你的手来判** ✓✓。

### 而探针的形状与前两个一致 ✓

⭐ **同一个骨架**（`spawn` vite ✓ + Playwright ✓ + `finally` 里**杀掉服务并退出** ✓✓ —— ⭐ **退出那一行是那 25 分钟换来的 ✓**），**同一个 CI 步骤位置**（`manual-verify.yml` 的 `audio` scope ✓），**同一种判据输出**（一行 `✅` 或一行具名的失败 ✓）。


## 十一、⭐⭐⭐ 业主的需求（2026-09-28 晚）：**新建项目**入口、模板、以及**轨道类型随时可改**

**原话要点** ✓：

* ⚠️ **现在 web 里没有好的"新建空白项目"入口** ✗；
* ⭐ **新建时可以选模板，也可以空白 ✓ —— 但空白也有【一条默认轨道】，而这条轨道的类型就是新建时选的那个** ✓✓；
* ⭐ **一根轨道的类型，随时可以改** ✓✓；
* ⭐ **模板提供几种就好 —— 常见的几种轨道搭配** ✓。

### ⚠️ 而第 3 条（**随时改类型**）推翻了我先前的一个假设

| 我先前的设计 ✗ | 现在的需求 ✓ |
|---|---|
| ⭐ **`kind` 是不可变的** ✓（**一个判别联合 —— 一条轨要么是采样器要么是合成器 ✓**） | ⭐ **`kind` 必须可改** ✓✓ |

⭐⭐ **而"可改"立刻引出一个必须先答的问题** ✓：**类型特有的字段怎么办** ✗✓？

| 字段 | 一条 `sampler` 轨改成 `instrument` 时 |
|---|---|
| ⭐ **`sample: { assetId }`** | ⚠️ **它描述的是"这条轨播哪个采样" ✗ —— 对合成器轨没有意义** ✓ → ⭐ **不能留着** ✗（**留着就是"模型允许、而语义不存在的状态" ✓ —— 判据里已经有一条守这个** ✓） |
| ⭐ **`takes: Take[]`** | ✅ **必须留着** ✓✓ —— ⭐ **take 是【内容】不是身份 ✓（业主早先的纠正 ✓）** —— **改成合成器轨之后，那段录音仍然是这条轨上录过的东西** ✓ |
| ⭐ **`selectedTakeId` / `takeRegions`** | ⚠️ **要一起看** ✓：**take 还在，选择就仍然有意义** ✓ |

⭐⭐ **所以规则应当是**：⭐ **改类型时，丢掉【只对新类型无意义、且属于路由/音源]的字段（`sample` ✓），保留【内容]的字段（`takes` ✓ 及其选择 ✓）** ✓✓。

⭐ **而这条区分不是新发明的** ✓ —— ⭐ **它正是业主早先那句纠正的直接推论** ✓✓：**"录音只是音频轨道的一种输入形式"** ✓ → ⭐ **输入形式变了，录过的东西还在** ✓。

### ⭐ 而"空白项目也有一条默认轨道"是一条好设计，理由要说清

⭐ 一个**空轨道列表**的界面 ✓，与**一条选中类型的空轨道**的界面 ✓，**对用户是两件事** ✓：

| | 空列表 | ⭐ **一条默认轨道** |
|---|---|---|
| 用户看到 | **一个"要做什么"的问题** ✗ | ⭐ **一个已经能开始的东西** ✓ |

## 十二、⭐⭐⭐ 业主的路障（2026-09-28 晚）：**"我没办法进入新界面，因为都有曲风在"**

⭐ 这不是一个功能请求，是一句**现场观察** ✓ —— 而它在代码里有一个**精确的位置** ✓：
