# 离线渲染的评测

TRACK B 要回答的是"44.1 kHz 那 24.4 秒花在哪"，方式是测量，不是重写。

## 已经测到的

| 量 | 值 | 怎么来的 |
| --- | --- | --- |
| 空 `OfflineAudioContext` | 4.8 ms / 4 秒音频（约实时的 0.12%） | 探针的基线档 |

前两条合起来说明：浏览器图本身的开销可以忽略，24.4 秒花在图的**内容**里。

## 展平的成本曲线：实测，且更正了一个流传的估计（2026-09-29）

`src/test/flattenCost.test.ts` 每次跑都会打印这条曲线（CI 也跑），本机实测：

```
   1 轨 ×  64 小节 =   1024 步 →  0.87 ms (0.851 µs/步)
   4 轨 ×  64 小节 =   4096 步 →  2.33 ms (0.569 µs/步)
  16 轨 ×  64 小节 =  16384 步 →  7.55 ms (0.461 µs/步)
  64 轨 ×  64 小节 =  65536 步 → 24.15 ms (0.368 µs/步)
   8 轨 × 512 小节 =  65536 步 →  3.84 ms (0.059 µs/步)
 100 轨 × 256 小节 = 409600 步 → 43.28 ms (0.106 µs/步)
```

最后一行是现实里最大的那一档，**0.106 µs/步**。按它投影到 2048 小节 × 100 轨 × 16 步：

```
  投影：0.106 µs/步 × 2048 × 100 × 16 ≈ 0.3 秒的展平
  数据：约 159 MB 的展平步进（JSON 作为代用指标），而六分钟八声道的音频缓冲约 1.1 GB
```

**所以之前流传的"5.5 µs/步、2048×100 大约 18 秒"这个估计已经过时了约六十倍**，而且它把风险说反了：一百轨的约束是**内存**，不是 JavaScript 时间。0.3 秒的展平在任何渲染预算里都不是问题；159 MB 的步进数据和 1.1 GB 的音频缓冲才是。

两个代用指标的边界要说明：步进那一列是 `JSON.stringify` 的长度，用来代替交给渲染器的数据量，不是分配器测量；音频缓冲那一列是算出来的，并在浏览器里量过。**展平的时间与"渲染要多久"是两件事**——这条曲线只管前者。

## 轨数成本曲线：怎么测

```
node scripts/measure_lane_curve.mjs --genre=chicago-house            # 1, 4, 16, 64 轨
node scripts/measure_lane_curve.mjs --lanes=16                        # 只测一档
node scripts/probe_arrangement_audio.mjs --only=lane --lanes=16 --json # 底层那一档
```

**每个轨数用一个干净的浏览器进程。** 这不是风格问题，是这台环境下唯一跑得通的方式，理由见下。

曲线测的是**时间与采样到的堆峰值**，而且要说清它测的不是什么：这些轨带一个解析不出任何采样的 `assetId`，所以曲线量的是**规划、轨道构建、主链与渲染**，不是采样解码或播放。堆峰值是采样值（每 10 ms 一次）因此是**下界**，只在 Chromium 里有，而且是**整页**的，不只是渲染那部分。

## 为什么分进程，以及这件事的边界

单次离线渲染就足以让浏览器进程消失：运行以 `[browser] disconnected` 结束，没有 `[crash]`、没有 `[pageerror]`、有时连限幅器的日志都没有——是整个进程没了，不是页面。逐条证据：

- 空闲的浏览器在同一环境里每 30 秒求值一次，活了至少 8 分钟（482 秒），三次开合各自正常求值并正常关闭。所以不是环境在掐长时间运行的东西。
- 同一个探针加不加堆采样**失败方式完全相同**，所以采样不是原因。
- `--only=lane` 跳过其余五个测量块之后仍然失败；把曲线提到所有渲染之前仍然失败——**一次两小节歌曲的渲染就够**。
- 多次运行死在不同的位置：有一次撑过两次渲染，有一次第一次渲染前就死。

**仓库早就知道这个形状。** `manual-verify.yml` 自己写着：159 个曲风的响度重录是分进程跑的，因为"单个浏览器进程在约四十次渲染后耗尽 WASM 预算并自行中止（所以它在笔记本上也从未跑完）"。曲线因此照同样的方式测。

**边界**：这台开发机上拿不到曲线数字本身。它属于 CI 的 `audio` 范围，那里有 `Lane cost curve` 这一步。说"没测到"比编一个数好，而这个项目已经收回两个编出来的数了。

## 图拆解：实测数字，以及它测不出什么（2026-09-30）

CI 的 `audio` 范围里"Arrangement audio"那一步早就带了一个**图拆解**：同一首歌渲染三遍（各自取三次采样的中位数），比较"完整图"、"绕过每轨 FX 链"、"关掉主链旋钮（响度修正、补偿增益、总线压缩——**不含限幅器**）"。

实测（`chicago-house`，约 90 秒的渲染）：

```
full              60.85 s   [59.28, 60.89, 60.85]
bypassFxRack      60.45 s   [60.14, 60.45, 60.83]   → 每轨 FX 链占 0.40 s
master knobs off  60.21 s   [59.13, 61.00, 60.21]   → 主链旋钮占 0.64 s
```

**必须一起读的话**：三次采样的离散范围是 **59.1–61.0 秒（约 1.7 秒）**，而要被归因的两项是 **0.40 秒与 0.64 秒**——**效应小于噪声**。所以这两行只能得到一句话：**每轨 FX 链与主链旋钮都不构成这次渲染的主要成本**，它们各自的占比落在这个测量的分辨力之下。

这也纠正了一个容易犯的读法：把 0.40 与 0.64 当成"精确的占比"是错的，它们是**两次中位数之差**，而同一配置的三次采样自己就能差 1.7 秒。

**推论**：约 60 秒的成本主要在别处（声部与合成/采样调度），要往下拆需要的是**分辨力更高的方法**（例如固定 CPU 亲和、更多采样、或把渲染切短到十几秒以降低抖动），而不是再加一个变体。

### 车道成本曲线：根因找到并修好，数字待下一次 CI（2026-09-30）

它连续两次四档全部超时，日志只有"no result within 420s"，**没有任何页面输出**。逐层查下来是**两处"解析了却没接上"**，都不是渲染问题：

1. **标志没有传进页面。** 探针在 Node 侧读了 `--only=lane` 与 `--lanes=N`，页面回调也解构了 `only` 与 `laneCount`，但调用处传的是 `{ genreId, ramp }`——于是页面里 `only === undefined`，**每次都跑完整套探针**（所有块、所有渲染）。而这条标志存在的意义正是"一档一个进程、先跑、别把浏览器累死"，本仓库自己的注释就写着"一个浏览器扛不过大约四十次渲染"。曲线块在完整流程里排在很后面，所以日志里没有它。
2. **提前返回只做了一半。** 页面在 `--only=lane` 时提前返回 `{ only, renderLaneCurve }`，但 Node 侧仍按完整摘要去读 `measured.fillBars`，直接崩掉——**这个标志从来没有端到端跑通过**。

修法：把两个标志接进 `page.evaluate`；Node 侧补上与页面提前返回对应的"打印并退出"；每档超时从 420 秒降到 180 秒（四档不再白等 28 分钟）；另外加了 Node 侧的**阶段标记**（等服务器/服务器就绪/页面已加载/开始求值），这样下次若还挂，日志会说出停在哪一步，而不是四个数字一样的 420 秒。

**判据**：新增 `src/test/probeWiring.test.ts` 检查**两侧的契约**——页面回调解构出的每个名字都必须出现在调用处传入的对象里，且 `--only=lane` 的提前路径必须在读取完整摘要之前（查的是去注释后的代码，因为第一版判据咬到了它自己解释这个 bug 的文字）。把缺陷放回去，两条判据会红。

**数字仍然待取**：修好的是管线，不是测量。下一次 CI 的 `audio` 范围会给出 1/4/16/64 车道的墙钟与峰值堆——在那之前这里没有数，按本项目的规矩写"没测到"而不是编一个。

## 一个被撤销的方向：为图拆解再加一条测量线（2026-09-30）

我一度派了一条独立线去做"图拆解"（给引擎加一个测量接缝：关掉声部/效果/混响/限幅，再写一个专门探针与 CI 步骤）。读完 CI 里已有的输出后撤销了它，理由是**这件事已经存在**：`scripts/probe_arrangement_audio.mjs` 早就在同一步里渲染了 `full` / `bypassFxRack` / `master knobs off` 三个变体并打印中位数。

**而且它已经给出了比"再加一个变体"更有用的结论**：这些部件的成本都落在测量噪声之下（见上一节）。所以那条线的产物会是一个更精致的接缝加上一组仍然读不出结论的数字——**不是这个项目需要的东西**。真正缺的是**分辨力**，不是更多变体。

记在这里而不是默默删掉：撤销一个方向的原因和做一个方向的原因一样值得留下。

## 车道成本曲线：数字到手，风险在时间而不在内存（2026-09-30）

这条曲线此前两次四档全部超时（见上一节的两处"解析了却没接上"）。修好之后，CI 的 `audio` 范围给出了数字——**每次渲染的片段长度相同（1,440,363 帧），所以这是一条干净的车道数曲线**：

| 车道数 | 墙钟（浏览器内） | 峰值堆（每 10 毫秒采样） |
| --- | --- | --- |
| 1 | **0.858 s** | 17.2 MB |
| 4 | **1.090 s** | 17.2 MB |
| 16 | **2.004 s** | 17.1 MB |
| 64 | **5.569 s** | 17.2 MB |

**怎么读它**：

- **固定开销约 0.8 秒**（1 车道就是 0.858 秒），此后每增加一条车道约 **+0.07 秒**（4→16 车道 12 条加 0.91 秒；16→64 车道 48 条加 3.57 秒）。按这个斜率外推，100 车道约 **8–9 秒**，2048 小节的长渲染里这个成本会被放大。
- **峰值堆完全不随车道数变化（17.1–17.2 MB）。** 这直接回答了"百车道是不是内存风险"：**在这个测量里不是，是时间风险**。而这个文档此前给出的 24.4 秒基线也是时间问题，两者一致。

**两个必须一起说的限制**：

1. **堆的读数是页面级的**，不是这次渲染自己的分配量（探针自己就这么写）。所以 17 MB 说明"加车道没有把页面堆推高"，**不能**说明"每次渲染只占 17 MB"。
2. **同一次运行里，重负载那一步的 64 车道读数是 6.127 秒 / 523.8 MB 堆**，与本步的 5.569 秒 / 17.2 MB 形成对照。差异来自**页面此前渲染过什么**——堆读数是页面当前状态，不是本次渲染的增量。把这两个数字放在一起看才诚实：曲线说明**斜率**，不说明绝对占用。

**这些车道是静音的**（探针的注释写着：随项目发布的目录是空的，这些车道指向解析不到任何东西的 `assetId`）。所以这条曲线量的是**图的构建与调度成本**，不是采样解码或回放成本——这一点必须跟着数字一起引用，否则"64 车道 5.6 秒"会被误读成"64 条采样轨播放 5.6 秒"。
## 音高测量换了两次，第三次才对（2026-09-30）

A4 判据（用 sfizz 的输出判断本项目的映射）用的音高测量**失败了两次**，两次的原因不同，都值得留在这里——因为"同一条判据又红了"最容易被人当成抖动而重跑。

**第一次：自相关取了峰的肩部。** 同一个 440 Hz 音、同一份字节相同的采样、渲染到两个不同目录，测出来 **880.01 Hz 与 890.52 Hz**。纯音的自相关峰是**平顶**的，音频里一丝差异就让选中的滞后差一个采样；约 50 采样一个周期，那就是 **2%**，正好是判据 1% 容差的两倍。把阈值收紧到 0.99×最大值**有帮助但没解决**：判据再次以 **1.195%** 失败。

**第二次：过零计数被包络带偏。** 换成过零后，同一条判据把 880 Hz 读成 **867.82 Hz**。原因是那条渲染带着库自己的**振幅包络**，而对衰减信号做**全局**均值扣除会留下一个移动的均值，让过零点不对称地偏移。

**第三次：频谱峰。** 用对数频率网格扫描幅度峰（音高是按比值判断的，不是按赫兹），在峰附近做两次抛物线细化。**包络无关**（衰减不改变某频率上的幅度），**峰的唯一性**也不依赖搜索规则。结果：880.00 对 880.00（0.00%），311.97 对 311.98（0.003%）。

**判据**把两次失败的具体情形都钉住了：同一个音测两次必须一致（相位差百万分之一弧度）、**衰减 40 dB 的音必须测出与稳定音相同的频率**，以及无音高素材（扫频）不得给高置信度——后者也修过一次：置信度原本拿峰值与**全网格**中位数比，而扫频的谱是平台、中位数很低，于是被判为"有信心"；现在与峰值 ±20% 频带内的中位数比，问的才是"这里有没有一个峰"。

# 离线渲染剖析（`RUST_DECISION.md` §五第 2 步）：实测

**日期** 2026-10-01，分支 `measure-render-profile`，脚本 `scripts/profile_offline_render.mjs`（可复现），
仪器在 `src/audio/WavExporter.ts`（`globalThis.__grooveRenderTimings`，**不设该标志时每一行都是空操作**）。

本节回答的就是本文开头那句话：**44.1 kHz 的整曲渲染，时间花在哪**。答案是本文此前没有预料到的那一个。

## 机器与负载（先说这个，因为它是本节的边界）

| 项 | 值 |
| --- | --- |
| CPU | **Intel Core i7-2635QM**（2011 年，4 核 8 线程 @ 2.0 GHz） |
| 内存 | 16 GB |
| 系统 / Node | CachyOS Linux / Node 22.22.3 |
| 浏览器 | Playwright 1.63 `chrome-headless-shell`，Chrome 153（另跑过 `channel: "chromium"`，结论相同） |
| **负载** | 本轮测量期间 `/proc/loadavg` 在 **2.4 – 23.4** 之间浮动；**同一台笔记本上另有三个 agent 在各自的 worktree 里跑 Chromium 渲染** ✓ |

**因此本节的每个数字都给两种**：**原始值** ✓，以及**用同页内联的"平凡图"对照渲染归一化后的值** ✓（0.5 s、4 个振荡器；空载 4.7 ms，测量中 2.9–11.2 ms）。
归一化不是装饰：**同一个 1 小节 `silent` 渲染，一小时内跑出过 11.0 s 与 15.2 s** ✓，**同一个 1 小节完整渲染跑出过 18.3 s 与 27.9 s** ✓。
**绝对值不可跨机器引用** ✗；**比例与排序可以** ✓。

## 夹具（固定、可复现）

`chicago-house` 经 `patternFromGenre` 展开后的完整图案 ✓：**8 条车道、128 步/车道** ✓，124 BPM ✓：

```
kick 32 拍 / snare 32 / hihat 32 / percussion 24 / bass 48 / chords 24 / lead 32 / fx 8   （1 小节 = 128 步）
chords = m1_organ、lead = saw_lead  →  实为本机解析为 GS-1 路由（voice）✓，由 wasm 核心经 AudioWorklet 发声 ✓
```

复杂度取 `bars`：**1 小节 = 17.18 s 音频**（124 BPM 下 7.7 s 图案 + 1.6 s 混响尾巴推导出的渲染尾）✓，**8 小节 = 125.56 s 音频** ✓（5,537,396 帧 × 44.1 kHz × 立体声）。

## 端到端（Node 侧包住整次 `page.evaluate`，含 WAV 编码与回传）

| 夹具 | 音频 | 原始墙钟（各次） | 归一化中位 | 折合 |
| --- | --- | --- | --- | --- |
| **1 小节（安静时段那组）** | 17.18 s | 17.95 / 23.35 / 24.25 s | **23.35 s** | **0.7× 实时** |
| 1 小节（更早两组） | 17.18 s | 18.46 / 18.98 s；18.98 / 20.34 / 27.36 s | — | 0.6–0.9× 实时 |
| **8 小节** | **125.56 s** | **511.28 / 445.71 s** | 中位 **481.21 s** | **0.2–0.3× 实时** |

**必须一起读的** ✓：1 小节那三次的**负载探针只差 2.8 → 3.5 ms（±25%）** ✓，而**墙钟差了 35%** ✓（17.95 → 24.25 s）✓——**所以这部分漂移不是机器负载** ✗，最可能是**渲染进程自己的状态** ✓（`RENDER_PROFILE.md` 上文记的堆/进程寿命问题 ✓，以及本节普查里那个"第二次读到 395 个节点"的观察 ✓）。**绝对秒数只在同一进程的同一次会话内可比** ✓。

⭐ **本机全速主渲染约等于实时、常常慢于实时** ✓✓（全部分组的中位都落在 **0.7× 实时** ✓）。这与本文 §一 表里"段落预览 **10× 实时**"**不矛盾但不通用**：
那个 10× 是 **8 kHz 单声道预览**路径 ✓——本节同一台机器、同一个浏览器里，同一条 `renderPatternOffline` 在 8 kHz 单声道下是 **5.86× 实时** ✓（受控、2 轮取中位 ✓）。
**"10× 实时"不能当作"全速渲染 10× 实时"来引用** ✗。

⭐ 而且**成本随音长超线性** ✓：音频长 **7.3 倍**（17.18 → 125.56 s），墙钟长 **18–28 倍**（17.95–24.25 → 445–511 s）✓。这一点本文此前的模型里没有 ✓。

## 相位拆分（方法：`performance.now()` 埋点，**不是猜**）

仪器落在 `renderPatternOffline` 真正有的接缝上；下表是 1 小节完整渲染的**中位数**，以及一次 8 小节渲染（两者形状一致）：

⚠️ **1 小节那一列来自更早、负载 4–5 的一组** ✓，所以它的"总计"是 **18.5–19.0 s** ✓，而本文端到端一节的安静时段中位是 **23.35 s** ✓——**同一台机器、同一夹具，差的是那 35% 的进程内漂移** ✓（见端到端一节 ✓）。**读数之间不要跨组相减** ✗，**每一项占同一列总计的比例可以读** ✓。

| 相位 | 1 小节 | 占比 | 8 小节 | 占比 |
| --- | ---: | ---: | ---: | ---: |
| `graph:master+genreFx`（主链 + 类型 FX + 混响 IR 构建） | 78–98 ms | ~0.5% | 78 ms | 0.02% |
| `noise:seedBuffer` | 1.4 ms | ~0.01% | 1.1 ms | <0.01% |

## 消融（差减法）：把主链、混响、限幅、声部分开

方法：同一图案渲染多次，每次**关掉一个阶段**（`directOut` ✓ / `bypassFxRack` ✓ / `masterBusCompEnabled:false` ✓ / 把混响的 IR 换成 1 帧静音 ✓ / 把其余车道清零 ✓），**轮流跑每一臂**（不是一臂跑完再跑下一臂 ✓——一臂 3 次连跑会把那个时间窗的负载漂移全算到它头上 ✓），取中位 ✓。

**必须一起读的限制** ✓：本机负载噪声（同一配置两次可差 30%+ ✓）**大于**几个小项之间的差 ✓。所以第二次运行时我把**同一臂跑两遍** ✓（`--arms=…,reverb-convolution,reverb-convolution,…` ✓）当作可复现性对照 ✓。

机器较安静时段（负载 2.2–3.7 ✓）的一轮，**3 次/臂、轮流跑、负载归一化** ✓：

| 臂 | 原始中位 | 归一化中位 | 折合 | 与 baseline 之差（归一化） |
| --- | ---: | ---: | ---: | ---: |
| `baseline`（完整） | 17.58 s | **20.46 s** | 0.84× 实时 | — |
| `reverb-convolution`（IR 换成 1 帧 → **卷积本身停掉**） | 16.24 s | **15.16 s** | 1.13× 实时 | **−5.30 s（≈ −26%）** ✓ |
| `silent`（全部车道无声，图全建） | 9.57 s | **9.56 s** | 1.80× 实时 | **−10.90 s（≈ −53%）** ✓ |
| `drums-only`（只留 kick 声部） | 10.80 s | 10.80 s | 1.59× 实时 | −10.71 s（负载更低的一轮里是 −6.03 s：这一档的**绝对值跨轮不稳**，只有"约等于 `silent`"这一点两轮一致 ✓） |

**可复现性** ✓：`reverb-convolution` 在同一轮里跑了 6 次（2 个重复臂 × 3 轮 ✓），归一化中位 **15.16 s** ✓，与另一个进程里单独一轮的 12.81 s 同向 ✓；两次都**明显**低于 baseline ✓。
作为对照，**同一台机器上同一臂在负载 20 时段曾读出过相反符号的差（−1.9 s / +6 s）** ✓——**这就是为什么本节的结论只用安静时段的读数，并把噪声写出来** ✓。

⭐ **结论五** ✓✓（百分比全部相对这一轮的 baseline **20.46 s** ✓）：

| 拆出来的项 | 归一化耗时 | 占 baseline | 怎么得到的 |
| --- | ---: | ---: | --- |
| **卷积混响**（sendA → 高通 → convolver，1.7 s IR） | **5.30 s** | **≈26%** | baseline − reverb-convolution（IR 换成 1 帧）✓ |
| **图结构本身**（总线、通道插入链、panner、duck；约 200 节点） | **4.29 s** | **≈21%** | reverb-convolution − silent ✓ |
| **声部与轨道效果**（振荡器、包络、鼓声模型、每轨 FX、延迟送） | **6.72 s** | **≈33%** | silent 之外的那一部分 ✓ |
| 其余（图构建、声部调度、GS-1 宿主、PDC、WAV 编码） | ≈4.1 s | ≈20% | 相位表 ✓ |

**两条推论** ✓：
1. **混响卷积是候选表里单项最大的一项** ✓（≈26% ✓）。这与本文开头列的五个候选里排第一的那个**相符** ✓，也**修正了**本节合成对照最初的错误读数 ✓（见结论三的 ⚠️）✓。
2. **"图"与"图里跑的卷积"要分开读** ✓：**图结构本身 ≈21%** ✓、**送进那张图的混响卷积 ≈26%** ✓——**两者是不同的问题** ✓：前者要**换结构** ✓，后者只要**别把卷积当默认总线** ✓（或换一条不做逐样本卷积的混响 ✓）。
   ⚠️ 这两个数**不要相加成"图占 47%"** ✗——silent 臂里那条混响总线**还在** ✓，只是没有信号喂它 ✓。

**这与 CI 已有的图拆解一致** ✓（本文上方 2026-09-30：`bypassFxRack` −0.40 s、`master knobs off` −0.64 s，而离散范围 1.7 s ✓）：
那两项当时就落在噪声之下 ✓，本节换用"内联对照 + 同臂重复 + 轮流跑"之后，**分辨力够了** ✓——这也印证了那边自己的推论："要往下拆需要的是分辨力更高的方法" ✓✓。
