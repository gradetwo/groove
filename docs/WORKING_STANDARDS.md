# 工作标准

这些不是建议，是做法。每一条都对应一次真实的返工或一次差点发出去的坏版本，理由写在每条下面——**没有理由的规则会被合理地违反。**

## 1. 等的时候开一个 worktree，别干等

一次发布要跑完整门禁、构建、体积、全量 CI（浏览器矩阵约半小时）。这段时间不能干等，也**不能**在主工作树上动手：发布的镜像同步发生在部署之后，它会复制**当前工作树**的内容，所以在发布期间改文件，会让标签指向一个我本仓里不存在的提交。

```bash
git worktree add ../groove-wt -b <分支名> HEAD   # 开一个独立工作区
cd ../groove-wt                                   # 在那里干活、提交
# 发布结束后回到主树合并：
git merge --no-edit <分支名>
```

用它的场合：发布在跑、全量 CI 在等、探针在跑、任何"要等几分钟以上"的事。改动不重叠时合并是干净的；重叠时 git 会说出来，比干等更早暴露冲突。

清理：`git worktree remove ../groove-wt`（分支保留）。

**新 worktree 缺的是未跟踪的生成资产**，跑门禁前先补一次，否则会看到一条假失败：

```bash
bash scripts/worktree_assets.sh        # 从主树拷 public/ 下未跟踪的文件，不覆盖已有
```

这条是实测出来的：`genreCovers.test.ts` 检查 `public/covers/<皮肤>/` 里的成品图，而它们大多是**生成且未跟踪**的——主树每套 159 张，刚建的 worktree 只有被跟踪的那几张，于是那条判据在 worktree 里红、在主树里绿。看起来像代码问题，其实不是。

## 2. 推送只走 `npm run push:dev`

它按顺序做三件事：**跑完整本地门禁 → 同步镜像 → 提交并推 `dev`**，并且会顺手取消被这次推送取代的 CI 运行。门禁不过就不推。

理由：连着两次因为"只跑了相关的几个文件"而推出红提交（一次是共享解析路径的改动，一次是新组件引入的字面色值让自动生成的皮肤表过期）。"记得跑整套"这条规则恰恰在人赶时间时失效，所以它是一条命令。

## 3. CI 分两层：开发推送跑快的，发版跑全部

| 什么时候 | 跑什么 |
| --- | --- |
| 推 `dev` | `validate`：类型、lint、单测、构建、bundle budget（约 5 分钟） |
| 推 `main`、开 PR、手动触发 | 以上 + 浏览器矩阵 |
| 发版 | `release.sh` 调 `npm run ci:full` **并等结果**，然后才部署 |

被推到发版的是**慢**的检查，不是**重要**的检查——`validate` 每次都会跑，它覆盖语法、行为与体积三类回归。

## 4. 发布期间不要动主工作树

同上第 1 条的理由。要动就开 worktree，发布结束后合并。

## 5. 发布路径的顺序是"先验后发"

`release.sh` 的步骤顺序是承重的：版本检查 → 新版本 → 本地门禁 → 构建 → 体积 → **全量 CI** → 部署 → 镜像 → 提交镜像 → 打标签 → 推送。部署成功是推 main 与打标签的前提。

这条在 2026-09-30 救了一次：一次发布已经走到"全量 CI"，我在等的时候发现编译把 `NoteEvent[]` 塞进了 `steps`（被 `as SequencerTrack` 断言盖住），于是**在部署前终止了发布**，线上仍是旧版本。如果部署在验证之前，那次就会把坏版本发出去。

## 6. 报结论要读内容，别读状态

`exit 0` 是状态，`1.81 GB` 是结果；"推送成功"是状态，"`git show <tag>:package.json` 的版本"是结果。凡是"这件事真的成立吗"的问题，去读那个东西本身。

同理：**不要把命令的输出截断**（`tail -N`／`head -N`）再下结论——这个项目里有四次缺陷是被截断的输出藏住的。

## 7. 一个改动落在共享路径上，就跑完整套件

"只动了一个组件"适合挑着跑；"所有调用方都会走这里"不适合。解析器、编译、清单桥接、设计 token 都属于后者。

## 8. 先写判据，再写实现；判据要能红

新增行为能力之前，先把"它对了是什么样"写成会失败的判据。**写完实现后把缺陷放回去验一次判据确实会红**——不会红的判据只是装饰。2026-09-30 那条编译判据就是这么验证的。

## 9. 缺口要么补上，要么写明理由

不写的例外等于没检查过。见 `src/test/mcpCoverage.test.ts`：会改动数据层模型的每个导出函数，要么有 MCP 工具，要么在一份带理由的例外表里；"暂时没做"不是理由。

## 10. 少用装饰性符号，说清事情

见 `docs/WRITING_STYLE.md`。这条来自业主的直接反馈。

## 11. 并行工作：一条线一个 worktree，验证交给远程 CI（2026-09-30）

业主的要求：

> 耦合度不高的工作就开几个agent worktree开发，反正用类似办法加速开发，多线异步推进，各种等待和阻塞时候都异步推进，多用worktree，CI/CD多用github远程跑。

做法：

```bash
git worktree add ../groove-wtN -b feat-<线名> next   # 一条线一个工作区、一个分支
bash scripts/worktree_assets.sh                       # 补未跟踪的生成资产（并让 git 忽略这些副本）
npm ci --no-audit --no-fund                           # 每个工作区自己的依赖
npm run push:branch feat-<线名> "<信息>"              # 推到 GitHub，让远程跑快检查
```

- **CI 触发已改为任何分支都跑快检查**（`push.branches: ["**"]`），浏览器矩阵只在 `main` 与发版派发时跑——这样每条并行线都有一条远程结论，而不必在本地反复整套跑。
- **一条线一个分支，`dev` 只由 `push_dev.sh` 在完整门禁之后发布**，所以半成品不会进到别人克隆的东西里。
- 多个 agent 同时改代码时，**每个 agent 有自己的工作区**；合并到 `next` 由我按验证结果做。
- 教训：`git add -A` 会把 `worktree_assets.sh` 复制进来的生成资产一起提交，CI 因此报"目录存在但封面不全"。脚本现在自己写 `.git/info/exclude`，但**提交前看 `git status`** 这条仍然要守。

## 12. 并发跑门禁的两个陷阱（2026-09-30）

多 worktree 并行之后，门禁本身出了两个问题，两个都是"读了结果才发现被误导"：

1. **失败日志用的是固定路径**（`/tmp/check_local_step.log`）。三个 worktree 各跑一次门禁，后跑的覆盖先跑的，于是**失败的那次会打印别人工作区的失败**。发现它的人是因为输出里的路径属于另一个 checkout。现在日志路径带 checkout 名与 pid，失败时还会打印**用的是哪个文件**。
2. **同一台机器上并发跑完整套件会让时序敏感的判据偶发失败**。实测：负载 24 时某个真实 sfizz 音高判据红了（880.00 对 880.01 Hz，容差 1%），单独跑两次都过；我自己的一次"失败"其实是**超时**（exit 124），不是判据红。

所以门禁现在持一把机器级的 `flock`：第二个套件会**等**，并说明它在等。**一次等待比一次假失败便宜。**

3. **锁只挡门禁，挡不住别的重活。** 加了锁之后，套件仍然红过一次：四个 worktree 在跑套件与构建时，`CompareViewLoudness` 变红，而日志里的 flatten 耗时是单独运行时的 **75 倍**（103 ms 对 1.4 ms）——单独跑就过。这是负载造成的第三次假红。

所以门禁在跑套件前会**读负载并等它降下来**：阈值取 `nproc`（每核一个可运行进程算"忙"，再多就不能信它的计时），最多等 15 分钟，等不到就明说"现在跑，计时失败没有意义"。**假红比不检查更糟**——它教人"红了就重跑到绿"。

推论：看到门禁红，先分清四种情况——**判据真的红了**、**超时了**（exit 124）、**打印的是别人的日志**、**机器被占满导致计时失真**。四者要采取的行动完全不同。
