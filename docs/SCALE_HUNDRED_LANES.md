# 上百条轨道会怎样？—— 以及"是不是就该上 Rust"

> 起因：业主问"轨道多到几十上百时，是不是就该迁到 Rust？现有架构有哪些问题？"（常见编曲确实几十上百轨 ✓）
> 本文只用**本仓库实测或已读到的事实**回答，并把**语言形状的问题**与**算术/架构形状的问题**分开 ✓。日期 2026-09-28。

## 一、先说结论：上百轨会压到**四件事**，而其中只有**一件半**是"语言"问题

| 压力点 | 这是语言问题吗 | 该做什么 |
|---|---|---|
| **① 渲染缓冲的内存** | ❌ **是算术** | 已实测：**6 min × 8 立体声 ≈ 1.1 GB** ✓✓。轨数**线性**放大 → 100 轨 × 6 min ≈ **13 GB** ✗✗。**Rust 不会改变 `帧 × 声道 × 轨`** ✗ —— 能改变它的是**流式/分段**（按乐章分别渲染 ✓）与**降低采样率做分析** ✓ |
| **② 每个声部的实时 CPU** | ✅ **是** | 现状是**每轨一条 Web Audio 节点链**（各连 `drumBusInput`/`musicBusInput` ✓ + send 进 `reverb.input` ✓）→ 上百轨 = 上百条链 + 上百个 worklet 声部 ✗。⭐ **把 N 个声部收进一个 worklet**（Rust/WASM 或合并的 JS worklet ✓）是**真实的架构收益** ✓✓ |
| **③ 拍平后的步进数组** | 🟡 **一半是** | `flatten` 把整首展开 ✓：`totalSteps = Σ 每小节 clip 步数` ✓ → 2048 小节 × 100 轨 × 16 步 ≈ **330 万个步进条目** ✗，若还是 **JS number 数组**则 ~100 MB 级 ✓。**Typed arrays 就能拿到大部分收益** ✓✓；Rust 只是**更彻底** ✓ |
| **④ 界面渲染** | ❌ **不是** | 100 轨 × 段落 × 单元格的 DOM/React 树 ✗ → **虚拟化**才是答案 ✓（与语言无关 ✓） |

## 二、⭐ 但上百轨最先撞到的**不是性能，是"决定按角色做"**

这是我认为最重要的一条 ✓✓，而它来自本周期**读代码的直接证据** ✓：

这套系统是在"**每种角色只有一条轨**"的前提下写成的 ✓：

| 位置 | 今天的形状 | 上百轨时会怎样 |
|---|---|---|
| `GROUP_BUS_ROLES` | 被测试断言为**恰好八个混音角色** ✓ | 一百条车道如何归总线 ✗ —— 按角色已经**不唯一** ✓ |
| `resolveMixTrackId` | 角色 → 混音（未知则**按名字**猜 ✓） | 多实例下"按角色"的默认值**含义模糊** ✗ |
| `DRUM_ROLES` | 四个鼓角色 ✓ | 40 条打击乐车道都进鼓总线 ✗（可能对 ✓，但要**明说** ✓） |
| **GS-1 路由** | `GS1_ROUTED_ROLES = ["chords", "lead"]` ✓，按**角色**发声 ✓ | 20 条和弦车道：**哪几条**交给 GS-1 ✗✓ |
| `SongSection.slots` | `Partial<Record<string, ClipSlot>>` ✓ | 一百个键的矩阵 ✓（可行 ✓，但**要按 laneId 而非角色** ✓） |

⭐ 结论 ✓：**`laneId` 是本周期才加进来的** ✓（它让"同一角色多条车道"**可表达** ✓✓），而**其余系统仍按角色做决定** ✗ —— 所以上百轨时，**第一类缺陷是"决定不唯一"（正确性）** ✓✓，第二类才是速度 ✓。**Rust 不会修第一类** ✗。

## 二·五 实测基线（2026-09-28，CI 的 audio scope，v2.34.18）

探针在 CI 上报出（[run 36434083672](https://github.com/gradetwo/groove/actions/runs/36434083672) ✓）：

```
render profile : 4s at 44.1kHz — empty context 0.0048s (the floor the browser charges), flatten 0.0028s (4 bars / 512 steps)
```

**把它除出来，得到两个可以直接用的数** ✓：

| 测量 | 换算 | 含义 |
|---|---|---|
| 空 `OfflineAudioContext`：**4.8 ms / 4 s 音频** | ≈ **实时的 0.12%** | ⭐ **浏览器的图底价可以忽略** ✓✓ —— 所以那 **24.4 s 花在图里的内容上**（声部 ✓ 效果 ✓），**不在机制上** ✓ → **拆图值得做** ✓✓，而 Rust **在这一层是有话可说的** ✓ |
| flatten：**2.8 ms / 512 步** | ≈ **5.5 µs/步** | ⭐ **这是"上百轨"的真正风险** ✓✓ —— 见下 |

**⭐ 用 5.5 µs/步 算一下上百轨** ✓（把算术写出来，好让人核对 ✓）：2048 小节 × 100 车道 × 16 步 ≈ **330 万步** ✗ → **约 18 秒**，**纯 JavaScript 的拍平开销** ✗✓ —— 而它**发生在渲染之前** ✓，所以它**与音频无关** ✓。

**这与我原先的猜测不同，而实测改了优先级** ✓：我以为内存是上百轨的第一道墙 ✓；**而拍平的时间与内存同量级地先撞上来** ✓✓（330 万条步进条目 + 约 18 秒 ✓）。它**纯数据** ✓ → **typed arrays 能拿走一大块** ✓✓，Rust 能拿走更多 ✓ —— 而这两条都**不需要先做音频迁移** ✓。

## 二·六 TRACK B 的第一台仪器**不合格**，而它指出了两件事（2026-09-28）

我想在本机再量一次拍平成本 ✓（纯数据 ✓ 不需要浏览器 ✓），于是写了一条会**打印**数字的测试 ✓。**跑出来的数字自相矛盾** ✓，我没有提交它 ✗✓ —— 因为**一个单位是错的测量，比没有测量更糟** ✓✓（它是"看起来像证据"的东西 ✓）。

两条发现 ✓，都值得记：

1. ⭐ **`totalSteps` 不是"车道 × 步数"** ✗✓ —— 我喂了 1 与 4 条车道，它**都报 1024** ✓（= 64 小节 × 16 步 ✓）→ 即它数的是**每小节的步数** ✓，**与车道数无关** ✓✓。这与我先前记下的"**已知的内部不一致**"（`totalSteps = Σ clipSteps(clip)` ✓ 而 `totalBars = 可播小节数` ✓）**是同一件事** ✓ —— 而它意味着：**任何把 `totalSteps` 当作工作量的地方，都会在车道数上少算** ✗✓；
2. ⭐ **第一行永远是预热** ✓ —— 1 车道报 **132 ms** ✓ 而 4 车道报 **3.6 ms** ✗✓（更多工作量更快 ✓）→ 那是 **JIT 预热** ✓✓ → **任何计时测量都必须先跑一次预热** ✓，否则第一条读数会污染整条曲线 ✓。

**所以下一步不是"再跑一次"** ✗，而是**把仪器修对** ✓✓：显式数 `车道 × 小节 × 每小节步数` ✓（**不要**用 `totalSteps` 当工作量 ✓）、**先预热** ✓、并且**把"测量"与"门禁"分开** ✓（计时断言在单元套件里就是一颗定时炸弹 ✓）。修好之后，那条曲线才会是"**上百轨**"与"**要不要 Rust**"两个问题都能站上去的数字 ✓。

## 二·七 ⭐⭐ 修好之后的曲线 —— 而它**推翻了先前那个投影**（2026-09-28）

仪器修对之后（**先预热** ✓、**显式数 `车道 × 小节 × 每小节步数`** ✓、**只打印不设门禁** ✓），读数**自洽了** ✓✓：

| 车道 × 小节 | 步数 | 耗时 | µs/步 |
|---|---|---|---|
| 1 × 64 | 1 024 | 0.61 ms | 0.596 |
| 4 × 64 | 4 096 | 1.68 ms | 0.410 |
| 16 × 64 | 16 384 | 5.62 ms | 0.343 |
| 64 × 64 | 65 536 | 22.66 ms | 0.346 |
| 8 × 512 | 65 536 | 9.45 ms | 0.144 |
| **100 × 256** | **409 600** | **44.77 ms** | **0.109** |

⭐⭐ **投影：2048 小节 × 100 车道 × 16 步 ≈ 0.4 秒** ✓✓ —— ⭐ **而先前记下的"≈18 秒"是预热伪影** ✗✓：CI 探针只量了**冷启动的那一次** ✓（2.8 ms / 512 步 = 5.5 µs/步 ✓），而**热的是 ~0.1–0.6 µs/步** ✓✓。

**所以结论要改** ✓，而且是往好的方向改 ✓：

* ⭐ **拍平不是"上百轨"的瓶颈** ✗✓ —— 100 车道 × 2048 小节约 **0.4 s** ✓（**这条比内存那条要轻得多** ✓）；
* ⭐ 而**"先预热再计时"这件事，影响了一个已经写进文档的结论** ✓✓ —— 也就是**仪器的一个缺陷，能让一个看起来很有说服力的数字错掉 40 倍** ✗✓（而这正是我先前撤下自己那台仪器时所依据的同一条理由 ✓）。

⚠️ **仍未测的**：**内存** ✓（上百轨的另一半 ✓ —— 按已知算术 **6 min × 8 立体声 ≈ 1.1 GB** ✓ → 轨数线性放大 ✓），以及**浏览器图内容那 24.4 s 的去向** ✓（拆图 ✓ —— 基线已证明底价只占 **0.12%** ✓✓，所以它值得追 ✓）。

## 二·八 ⭐ 受控实验：**"车道比步数更贵"被否证了**（2026-09-28）

曲线里有两行**步数相同**（65536 ✓）而耗时差 **14 倍**（`64×64` = 108.66 ms ✓ vs `8×512` = 7.53 ms ✓）→ 我把它记成**一条带数字的假设** ✓ —— 然后**做了受控实验** ✓：把步数**固定**在 65536 ✓，只动车道数（`bars = 4096 / lanes` ✓）：

```
fixed steps :   4 lanes × 1024 bars = 65536 steps → 5.63 ms
                8 lanes ×  512 bars = 65536 steps → 5.56 ms
               16 lanes ×  256 bars = 65536 steps → 3.55 ms
               32 lanes ×  128 bars = 65536 steps → 5.61 ms
```

⭐ **固定步数下耗时基本是平的** ✓✓ —— **所以"车道主导"是错的** ✗✓，先前那个 14 倍**是离群值** ✓✓。

**而这次实验还带出第二条更重要的结论** ✓：同一份代码的 µs/步在**不同运行之间从 0.06 到 6.4** 波动 ✓✓ —— 所以：

* ⭐ **这里的任何单次读数只能当数量级用** ✓ —— 投影是 **0.4 s 到 ~2.5 s** ✓，两条都远低于"瓶颈" ✓；
* ⭐ **而"拍平不是上百轨的瓶颈"这个结论是稳的** ✓✓ —— 因为**它的上界**也只有几秒 ✓，而内存那一侧的对照是 **159 MB vs 1.1 GB** ✓。

**这一整段的规矩在这里表现得很清楚** ✓：**一个数字产生一个假设 ✓；一个受控实验否证了它 ✓；而否证与确认同样是收获** ✓✓ —— 我把它记下来，而不是把那条线索留在文档里当"可能的原因" ✓。

## 二·九 ⭐⭐⭐⭐ TRACK B 的拆图：**渲染时间的大头是声部与图，不是效果器**（2026-09-28，CI 的 audio scope）

探针用**它已经在用的开关**（`bypassFxRack` ✓ —— 不写第二套建图代码 ✓）做了配对测量 ✓：

```
render split  : full 72.3331 s  vs  bypassFxRack 53.506 s
                → 效果机架 = 18.8271 s
                → 余项（声部 + 节点图 + 母带）= 53.506 s
render profile: 空上下文 0.0039 s   ← 浏览器的底价
```

**除出来** ✓：

| 份额 | 数值 | 含义 |
|---|---|---|
| ⭐ 浏览器的底价 | **0.0039 s / 72.33 s ≈ 0.005%** | **机制几乎免费** ✓ —— 时间花在**内容**上 ✓✓ |
| ⭐ **效果机架** | **18.83 s ≈ 26%** | JS worklet + 节点图的成本 ✓ |
| ⭐ **余项**（声部 + 图 + 母带） | **53.51 s ≈ 74%** | ⭐ **大头在这里** ✓✓ |

### 这回答了"是浏览器的机制，还是我们的代码"

⭐⭐ **是我们的代码** ✓✓ —— 浏览器的图机制只占 **0.005%** ✓，而 **74% 花在声部合成与节点图上** ✓。

### 而它对"要不要 Rust"意味着什么

* ⭐ **74% 那一块，正是"把 N 个声部收进一个音频线程"所针对的东西** ✓✓（见 [`RUST_DECISION.md`](RUST_DECISION.md) ✓）—— 也就是说 **Rust 要修的是对的那一块** ✓；
* ⭐ **26% 是效果机架** ✓ —— 也在 worklet 里 ✓，但**是另一件工作** ✓；
* ⚠️ **而余项里的"母带链"部分仍未分开** ✗✓ —— 这个配对**分不开**它们 ✓，所以它**被标为余项，而不是被归给谁** ✓✓。要分开它需要下一个配对 ✓（用探针里那个 `masterless` 开关 ✓ —— ⭐ **而我会先读它的定义再用** ✓✓）。

## 三、那就该上 Rust 吗？——**先测成本曲线，再决定**

Rust 在这里的价值（与 `docs/RUST_DECISION.md` 一致 ✓）：**② 声部收进一个音频线程** ✓ 与 **③ 步进数据的紧凑表示** ✓。
它**不能**解决：**① 内存的算术** ✗、**④ UI** ✗、**以及第二节那类"决定按角色"的问题** ✗✓。

⭐ 所以顺序应该是 ✓：

1. **先测"每车道成本"** ✓✓（TRACK B 的剖析延伸一步 ✓）：同一首歌渲染 **1 / 4 / 16 / 64 条车道** ✓，报**墙钟与峰值内存** ✓ → 得到一条**成本曲线** ✓；
2. **同时清掉"按角色做决定"的地方** ✓（把决策键从**角色**改成 **laneId** ✓，并为每一处写判据 ✓）—— 这件事**与语言无关** ✓，而且**上百轨时它是前提** ✓✓；
3. **只有**当曲线显示"**单车道成本 × N** 不可接受"**且**"合并成一个 worklet 能显著改变它"时 ✓，才谈把声部层迁到 Rust/WASM ✓ —— 那时**判据**也已经现成 ✓（"Rust 声部 与 浏览器图 逐样本一致" ✓，与 sfizz 交叉验证同一形状 ✓✓）。

## 四、一句话

**上百轨是常见需求，而现在最先挡路的不是语言** ✗ —— 是**"按角色做决定"在多实例下不再唯一** ✓，以及**整曲缓冲的内存算术** ✓。
**Rust 值得为"声部集中到一个音频线程"与"紧凑步进数据"而做** ✓，但**要先有那条成本曲线** ✓，而且它**不该被当作内存与 UI 问题的答案** ✗。
