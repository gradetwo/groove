## 二·五、P0 的根因（读代码得到的，而不是猜的）

**为什么 `render_song` 没有进度**：整首歌在 **Node 侧只有一次** `renderAudio(pattern, options)` 调用（`flattenMcpSong` 把整首歌拍平成**一条** pattern，
`mcp/song.ts`），而真正的耗时发生在页面里的 **`OfflineAudioContext.startRendering()`** 上 —— 那个调用**不提供任何进度回调** ✓✓。所以"无进度"不是
忘了加日志，而是**当前架构拿不到中间状态**：Node 侧没有循环可挂 ✓，页面侧没有可轮询的计数 ✓。

**因此唯一的真解是"分块渲染"**，而它恰好已经具备全部前提：

* 导出器**本来就接受 `options.bars`**（`src/audio/WavExporter.ts:296`，上限 64）✓ —— 也就是**可以只渲染一段小节** ✓；
* 拍平结果**本来就返回 `boundaries`**（`src/features/arrangement/songFlatten.ts:293`）✓ —— 也就是**段落边界的位置是已知的** ✓；
* 于是 `render_song` 可以按段落（或按固定小节数）**逐块调用**、在块与块之间**回报 N/M 小节**、并把 WAV 块**顺序拼接** ✓✓。

⚠️ 拼接需要一条判据（同采样率/同声道/同格式 ✓），而块之间**不能**各自重新应用母带链 ✗ —— 那会把限幅器与响度归一化**逐块各做一遍** ✗✓，
产生段落级的电平跳变 ✓。所以分块必须在**同一母带处理之前**完成 ✓，或者拼接后再过一次母带 ✓ —— **这是分块方案里唯一有技术风险的一步**，值得先写判据再写代码 ✓。

**在那之前，能给作曲家的诚实答案是**：把**实测的耗时量级**写进描述 ✓（数字用 CI 音频探针测 ✓，不用估 ✓），并明确说明"**本轮渲染无法回报进度，请用 `maxDurationSec` 事前拒绝，或用 `render_audio` 分段渲染**" ✓ —— 一份能把黑盒的边界说清楚的描述 ✓，比一句"reports no progress"更有用 ✓。

## 二·八、⚠️ 更正我在上一轮的警报：64 是**每段落**上限，不是全局截断

上一轮我写下"512 小节的歌被拍平成 64 小节，可能 87.5% 的编曲从未被渲染"，并把它称为**可能远高于报告的 P0**。**那是错的** ✗✓，原因在我的**夹具**：

`MAX_SECTION_BARS = 64`（`src/types/song.ts:141`）是**单个段落**的上限 ✓，而我的夹具把 512 小节全放进**一个**段落里 ✗✓ —— 于是被钳到 64 ✓。
**一首 348 小节的歌是用多个段落表达的** ✓（报告的作者正是走 `add_section` ✓），所以**不存在全局截断** ✓✓。我把一个夹具错误升格成了 P0 猜测 ✗ —— 记在这里，因为"用一次测量去推翻一个猜测"是这套流程的价值，**而它同样能推翻我自己的猜测**。

**顺带查清了三件事**（它们比那条假警报有用）：

| 路径 | 行为 |
|---|---|
| **MCP `add_section`** | zod `.max(64)` ✓ —— **超过就报错** ✓（**响亮的** ✓✓，报告用的 `bars: 44` 完全合法 ✓） |
| **URL 分享** `SequencerUrlShare.ts:331` | 越界**直接跳过该段落** ✓（也是响亮的 ✓） |

**还剩一条真实的内部不一致** ✓：`totalBars = playable.length`（按段落展开的**小节条目数** ✓）而 `totalSteps = Σ clipSteps(clip)`（每个条目加**整个 clip** 的步数 ✗✓）→ 于是"1 小节段落 + 128 步 clip"得到 `totalBars: 1` **和** `totalSteps: 128` ✓✓。渲染器用 `totalSteps` 排事件 ✓、用 `totalBars` 算时长 ✓ → **两者会互相矛盾** ✓。这条仍然待查 ✓（不是夹具问题 ✓），但它影响的是"一个比段落更长/更短的 clip 如何被摆放" ✓，**不是长歌的截断** ✓。

**给报告 P2.6 的诚实答复** ✓：512 小节是**全程**上限 ✓、64 小节是**段落**上限 ✓，两者不同 ✓；要写更长的曲子就**多用段落**（这正是它被设计的方式 ✓）；真正该补的是**在 `add_section` 的 `bars` 上写明这条** ✓，而不是让调用方从 zod 的通用报错里推 ✓。

## 二·九、更正：分块渲染的前提**并不**都已存在（我上一轮写乐观了）

我写过"导出器本来就接受 `options.bars`、拍平本来就返回 `boundaries`，所以前提都已具备"。**前半句是错的** ✗：

```ts
const bars = Math.max(1, Math.min(64, Math.floor(options.bars || 1)));   // WavExporter.ts:297
const totalSteps = patternSteps * bars;                                  // :318
```

`bars` 是**重复次数**，**不是小节偏移** ✗✓ —— "渲染第 40–100 小节"**今天无法表达** ✓。

**真正的前提清单**（其中一条让工作量比看上去小）：

| # | 需要什么 | 现状 |
|---|---|---|
| 1 | **一个小节区间** | ❌ 导出器无偏移参数。**但不必改导出器** ✓：拍平后的 pattern 是"整首歌的步进数组" ✓，所以**切一个区间 = 切 steps 的 `[from*16, to*16)` 片段** ✓✓，再用 `bars: 1` 渲染这一片 ✓ —— 于是偏移这一步**不需要动导出器** ✓ |
| 2 | **母带链不得逐块各跑一遍** | ❌ **这一条真的需要改导出器** ✓ —— 现有选项里没有"跳过母带"（`sampleRate` / `channels` / `loudnessTrimDb` / `bars` / `swing` / `stemTrackIdx` ✓ 都不是 ✓）。否则限幅器与响度归一化会**逐块各做一次** ✗ → 段落级电平跳变 ✓ |
| 3 | **WAV 拼接** | ❌ 没有现成的拼接器 ✓，但同采样率/同声道/同格式下是**纯字节追加** ✓（只需处理一次 WAV 头 ✓），可在 Node 侧用现有写入器做 ✓ |
| 4 | **判据** | ❌ 待写：分块拼接 vs **单次整曲**渲染，**逐样本在 epsilon 内** ✓；并在段落边界取样确认**无电平跳变** ✓ |

**所以 P0 的正确拆法**（按风险从低到高）：

1. 先在导出器里加"**跳过母带**"这一个选项 ✓（最小 ✓、可被现有渲染测试守住 ✓：不传时逐字节不变 ✓）；
2. 再在 `render_song` 里按 `planRenderChunks` **切片 + 逐块渲染 + 拼接** ✓，块间回报 **N/M 小节** ✓；
3. 最后把 **audio scope 的判据**接上 ✓（拼接 vs 整曲逐样本一致 ✓ + 边界无跳变 ✓）。

**在那之前叙述上能做的、且已经做了的**：描述里说明该调用**报不了进度** ✓、给出 `maxDurationSec` 事前拒绝 ✓、并指明替代路径 ✓ —— 唯一还缺的是把**实测耗时量级**填进去 ✓（数字要来自探针 ✓）。
