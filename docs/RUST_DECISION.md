# 在 groove 内部做，还是新开项目？以及 Rust 该不该进来

> 起因：`wow` 提案的评估结论是"groove 缺的是 **SFZ 真实乐器** 与（可能的）**原生整曲渲染**"。业主随即决定：**那就在 groove 内部实现，不必新开项目**；并追问：**性能与延迟上，是不是该用 Rust？groove 里有哪些工作应当迁到 Rust？**
> 本文只用**这个代码库实测过的数字**回答。日期 2026-09-28，基线 v2.34.18。

## 一、先看实测：groove 慢在哪里，以及**不慢在哪里**

| 实测项 | 数字 | 它说明什么 |
|---|---|---|
| 段落预览渲染 | **14.4 s 音频 / 1.45 s 墙钟**（≈ **10× 实时**） | ⭐ **DSP 本身不慢** ✓ —— 它比实时快一个数量级 ✓ |
| 分析通道（8 kHz 单声道） | **1.8 s**（同一首歌在 44.1 kHz 是 **24.4 s**） | 杠杆是**采样率与声道数**（**13.5×** ✓），**不是语言** ✓ |
| 同运行时确定性 | **0.005 dB** | 现状可复现 ✓ —— 任何迁移都必须守住这条 ✓ |
| 主限幅器延迟 | **7.415 ms**（预测 7.408 ✓） | 延迟已经被**实测**过 ✓，不是估算 ✓ |
| 音频车道路径延迟 | **0 ms**（脉冲实测 ✓） | 新路径没有引入延迟 ✓ |
| `OfflineAudioContext.startRendering()` | **没有回调** | ⭐ **真正的瓶颈是架构，不是速度** ✓✓ |
| 长曲内存 | 6 min × 8 立体声轨 ≈ **1.1 GB** | 内存是问题 ✓，而它就是上面那条的直接后果 ✓ |

⭐ **结论一**：**按实测，groove 的痛点不是算力** ✗ —— 是"**渲染是一个跑在浏览器里的黑盒**" ✓（无进度 ✓、需要 Chromium ✓、内存峰值 ✓、分块不等价 ✓）。**这四件事里没有一件是"换语言"能解决的** ✓✓。

## 二、那么性能/延迟的问题，Rust 帮得上吗？

| 环节 | Rust 是否更快 | 理由 |
|---|---|---|
| `decodeAudioData` | ❌ 不会 | 它是浏览器原生的 C++ ✓，换成 Rust 只是把同一件事做第二遍 ✓ |
| 声部合成（worklet） | ❌ 不会 | 它已经在实时线程上跑 ✓，且**不是**瓶颈 ✓ |
| 段落预览（10× 实时 ✓） | ❌ 不会 | 已经比实时快一个数量级 ✓ |
| **离线渲染去掉浏览器** | ⭐ **可能，但方式不唯一** | 目的是"**不在浏览器里**" ✓ → Rust+WASM 是一种手段 ✓，把现有 TS 引擎搬到 Node 是另一种（代价更大 ✓） |
| **SFZ 解析 + 磁盘流式 + SAB 环** | ✅ **会** | 这里 Rust 的收益是**结构性的**（零拷贝 ✓、无 GC 抖动 ✓、可预测的内存 ✓），不只"更快" ✓ |

⭐ **结论二**：**Rust 该不该进来，取决于"要不要离开浏览器"，而不取决于"要不要更快"** ✓。

## 三、如果 Rust 进来，边界应该画在哪

**应当考虑迁的（按理由强度排序）** ✓：

1. ⭐ **离线渲染核心**（声部图 + 效果链 + 母带 + 导出）——**唯一有实测动机的迁移** ✓✓：它必须能**在没有浏览器的情况下**跑 ✓（这正是路线图 Phase 0 里那条**至今未做**的 RenderTarget ✓）。而且它天然是跨宿主的 ✓（浏览器用 WASM ✓、Node 用原生 ✓）= `wow` 文档里"**一份核心两个宿主**" ✓ 的正确用法 ✓ —— **但范围是"渲染"，不是"采样器"** ✓。
2. **采样器（SFZ + 流式）** ✓ —— 前提是 **SFZ 真被需要** ✓（产品问题 ✓）；收益是结构性的 ✓（见上表 ✓）。
3. **分析通道**（8 kHz 单声道 ✓）—— 收益有限 ✗（杠杆在采样率 ✓ 已被利用 ✓），**除非**要它跑在 Node 里 ✓。

**不该迁的** ✓：

| 不迁 | 理由 |
|---|---|
| **UI / 视图** | 零收益 ✓，且会切断热重载与测试链 ✓ |
| **曲风数据（159 个 ✓）** | 它是**内容** ✓ —— 搬进 Rust 会让**编辑与评审变难** ✓✓（真实成本 ✓，换不来运行时收益 ✓） |
| **MCP 服务器** | 它是薄薄的 JSON-RPC 层 ✓；它的问题**全是消息质量**（如未知名 genreId ✓），不是速度 ✓ |
| **门禁与探针** | 它们的价值在**可读性** ✓（人读一行就知道是哪一步 ✓） |

## 四、⭐ 一条本仓库付过代价的反对意见，必须摆上桌

这个代码库最强的资产是：**一个事实只在一处定义** ✓、**3224 项测试** ✓、**一条会指名失败步骤的门禁链** ✓✓ —— 而这条工作流里反复抓到的缺陷**全都是**"**两处算同一件事**" ✗（`step * stepDur` 与前缀和 ✓、`bars` 的两个含义 ✓、六个硬编码的"四" ✓、`isDrumTrack` 按名字猜 ✓）。

> **引入第二种语言，等于把"两处算同一件事"的**表面积**翻倍** ✓✓ —— 因此 Rust 的迁移应当**由实测需求驱动** ✓（上面第 1、2 条 ✓），并且**边界要窄** ✓：**一条路径** ✓，且**跨语言边界用判据围起来** ✓✓ —— 例如"**Rust 核心与浏览器图，逐样本一致**" ✓（与 sfizz 交叉验证同一形状 ✓）。

## 五、我建议的顺序（把决定推迟到有数据的时候）

1. **第一步：SFZ 子集，留在 vault 内部、留在 TypeScript** ✓（**不开新项目 ✓、不引入 Rust** ✗）—— 三个注入点**已经等在那里** ✓（`planAudioLaneEvents` ✓ / `createSampleLoader` ✓ / `SampleSink` ✓）；
   **判据**：与 **sfizz** 对同一个 `.sfz` 的输出**逐样本在 epsilon 内** ✓✓（把 `wow` 文档的 P6 交叉验证提前到第一步 ✓）。
2. **第二步：给离线渲染做一次剖析** ✓✓（不是重写 ✓）—— 44.1 kHz 那 **24.4 s** 究竟花在哪 ✓：声部合成 ✓ / 效果器 ✓ / 混响卷积 ✓ / 限幅器 ✓ / 重采样与 WAV 写出 ✓。**没有这个数字就谈 Rust，是在解决一个还没被测量的问题** ✗。
3. **第三步：只有当"离开浏览器"成为真需求时** ✓，才做**渲染核心**的跨语言迁移 ✓（WASM + 原生 ✓），**并同时**要求"逐样本一致" ✓ 与"确定性哈希不变" ✓ 两条判据 ✓。

## 六、一句话结论

**在 groove 内部做是对的** ✓（`wow` 那份文档最值钱的部分是"一份核心、两个宿主"，而它**不需要**一个新仓库来成立 ✓）。
**Rust 不是性能答案** ✗ —— 实测显示 DSP 已经 **10× 实时** ✓；Rust 是"**离开浏览器**"与"**采样流式/解析**"这两件事的**手段** ✓。
**因此顺序是：先 SFZ（TS，在 groove 里 ✓）→ 再剖析离线渲染 ✓ → 才谈把渲染核心迁到 Rust ✓**，并且**每一条跨语言边界都配一条"逐样本一致"的判据** ✓✓。

## 七、业主决定（2026-10-01）：Phase 0 引擎下沉**要做**，路径不限定

**路径开放** ✓：先前那条 ⛔ 针对的是"**手写第二份 Node 渲染器**" ✗，不是 Rust 本身 ✓。因此"**纯 Rust 本地 server**"是合法手段 ✓，前提是它满足 §四 的三条：**由实测需求驱动** ✓、**边界窄** ✓、**跨语言边界有判据** ✓。

**候选的"唯一共享物"** ✓：`/home/crow/music/synth/crates/synth-core` ✓（我看到了目录与 `Cargo.toml` 的名字 `synth-core` ✓）。**但尚未核实**它是否就是 wasm 那份 DSP 的**同一源** ✗✓——这正是最该先量的一件事 ✓：若同源 ✓，"第二个声音"的风险**从结构上消失** ✓✓（这正是 §四 想要的形状 ✓）；若不同源 ✗，那么它就是**第二份实现** ✗，必须先按 §四 的要求把边界围起来再谈 ✓。

## 八、业主政策（2026-10-01）：**适合的，逐步迁移到 Rust**

**业主原话**："本项目适合迁移到rust的，都应该逐步迁移"。

**这条政策的方向与本文的实测结论一致** ✓——本文从没说过"不用 Rust" ✗，说的是：**Rust 不是性能答案** ✗（DSP 已 10× 实时 ✓），它是"**离开浏览器**"与"**采样流式/解析**"这两件事的**手段** ✓。业主已经决定"离开浏览器"要做（§七 ✓），所以这条政策落在**同一个方向上** ✓。

**但"适合"必须由测量定义** ✓✓——否则"逐步迁移"会退化成凭感觉搬代码 ✗，而本文 §四 已经量过代价：**引入第二种语言会把"两处算同一件事"的表面积翻倍** ✗✓（这条工作流抓到的缺陷**全都是**"两处算同一件事" ✗）。因此每一步迁移都要**同时**满足：

1. **有实测的痛点** ✓——由**本文第 1、2 节那种数字**指认 ✓（例如剖析显示时间花在卷积 ✓ / 内存峰值 ✓ / 解析与流式 ✓），**不是**"Rust 大概更快" ✗；
2. **边界窄** ✓——一次一条路径 ✓，不做"顺手把周围也搬了" ✗；
3. **边界上有一条判据** ✓✓——**逐样本一致** ✓ 或**确定性哈希不变** ✓（基线 **0.005 dB** ✓，见 §五第 3 步 ✓）；
4. **共享物唯一** ✓——两条路径必须共用**同一份** DSP/解析核心 ✓（若不同源 ✗，那就是"第二份实现" ✗，按 §四 先围边界 ✓）。

### 按本文自己的表，候选与"不该动"的（逐项）

**候选（有结构性收益，不只是更快）** ✓：**SFZ 解析** ✓、**采样磁盘流式** ✓、**共享内存环** ✓（零拷贝 ✓、无 GC 抖动 ✓、内存可预测 ✓）——以及**渲染核心**本身 ✓（§七 已触发 ✓）。

**明确不该迁移的** ✗（本文 §三 的实测/成本理由 ✓，逐条保留）：
* **UI / 视图** ✗——零运行时收益 ✓，且会切断热重载与测试链 ✓；
* **曲风数据（159 个）** ✗——它是**内容** ✓，搬进 Rust 会让**编辑与评审变难** ✓✓；
* **MCP 服务器** ✗——薄薄的 JSON-RPC 层 ✓，它的问题**全是消息质量**（如未知名 genreId ✓），**不是速度** ✓；
* **门禁与探针脚本** ✗——它们的价值在**可读性** ✓（人读一行就知道是哪一步 ✓）。

**不变的两条** ✓：**不开新仓库** ✓（在 groove 内部做 ✓）；**每一条跨语言边界都配一条判据** ✓✓。
