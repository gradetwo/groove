# 发布

`package.json` 的 `version` 是唯一需要手改的地方，改完跑 `npm run version:sync`，然后 `bash scripts/release.sh`。

## 八步

```
version:check   版本四处一致
local gate      typecheck / lint / styling / tests
build           vite build
deploy          deploy:only（含启动探针）
mirror          把本仓已提交的文件复制进镜像仓并逐文件核对
mirror commit   把复制进去的东西提交并推 dev
tag             两个仓各打一个标注标签，并读 package.json 确认指向对
remote          推 dev，并检查 origin/main 是 origin/dev 的祖先
```

脚本在第一步失败就停，并说出是哪一步。这是为 v2.34.25 写的：那次的 deploy 失败了，而 main 和 tag 照旧被推了上去，线上是坏的而仓库说是好的。

## 顺序的规则

`deploy` 的位置是承重的。它之前的一切都只是关于构建的说法，它之后的一切都是关于线上是什么的说法。所以：

- 部署成功是推 main 和 tag 的前提。脚本自己保证这一点。
- 不要在发布跑的时候手工推镜像或 main。这条是我犯过的错：v2.34.31 发布期间我顺手推了镜像，等于绕过了上面那条前提。那次部署恰好是成功的，所以没造成后果，但顺序本身是错的，而它出错的方式是"看起来没事"。

如果确实需要在发布之后收尾，等 `release.sh` 退出再做。

## 部署之后的失败

`deploy` 之后、`remote` 之前的失败留下的是一个部分发布的版本：线上是新的，main 和 tag 不是。v2.34.29 就是这样，而脚本当时说的话是错的（它说"什么都没发布"，而线上已经在服务新版本）。现在失败路径按 `DEPLOYED` 标记分两句：部署前照旧说没发布，部署后明说线上已经是这个版本而 main 和 tag 不是。

## 怎么核对

不要读"推送成功"，读文件。三处各读一次：

```
线上   curl -s https://groove.wangda.today/version.json
dev    git -C ../release/groove-github show origin/dev:package.json
main   git -C ../release/groove-github show origin/main:package.json
tag    git -C ../release/groove-github show v<version>^{}:package.json
```

四个数都等于要发布的版本，才算成了。标签那一步用的就是这个判据：它不去看推送是否成功，而是拿 `-S` 找出承载该版本的提交，找不到就退出。v2.34.29 的标签就是这样被发现的——线上和部署都没问题，标签根本不存在。

## 推送被拒的几种情况

都会遇到，而处理方式不同：

| 现象 | 性质 |
| --- | --- |
| `Permission denied (publickey)` | SSH 认证，通常是瞬时，重试一次 |
| `remote rejected ... Internal Server Error` | GitHub 服务端，瞬时，重试一次 |
| `dev -> main` 被拒而 `dev` 成功 | 非快进。镜像仓里 main 本来就该等于 dev，用 `--force` 对齐 |

第三种容易被误读成认证问题。分辨方式是读错误的第一行，而不是最后一行——第一行说原因，最后一行只说"请确认你有权限"。


## 推完之后必须看 CI，看的是 CI 不是本地门禁

加这一节的原因是一次真实的失败：2026-09-28 到 29 之间，每一次推 `dev` 都失败，连续四十次，而全部失败在同一个步骤上——bundle budget。本地门禁不构建，所以看不见它；也没有别的地方在看它。于是"本地门禁通过"被读成了"这样就行"。

```
npm run ci:status     # 最近几次 CI，以及失败时是哪一步
npm run ci:watch      # 等这次跑完再报告，退出码就是 CI 的结论
```

两件事因此改了：

1. **bundle budget 进了发布路径**，位置在 `build` 之后、`deploy` 之前。它原来只在 CI 里，而 CI 的失败并不阻止部署——一个在"反正会部署"的流程里只做标注的检查，是注释而不是门禁。
2. **本地门禁仍然不构建**，这是有意的（它要快）。所以体积、端到端和探针这些需要构建或浏览器的检查，判定权在 CI；而读它们的责任在这里这条命令上。

一条能记住的说法：**本地门禁通过只说明本地门禁通过。**


## 改了行为就跑全套，别只跑相关的那几个文件

同一个晚上犯的第二个同类错误：给 `tuneCents` 接上控制器调音之后，我只跑了 SFZ 相关的几个测试文件，本地是绿的，于是推了上去。CI 立刻红了——`src/test/realLibrary.test.ts` 里有一条测试断言"鼓不应该被移调"，而它读的是**真实的库**，不在我跑的那几个文件里。

判据本身没错、代码也没错（那个 region 确实带两个调音旋钮，各 +600 音分），错的是**我选了子集来验证一个会改变所有解析结果的行为**。

规则：**改动落在共享的解析/计算路径上时，跑 `scripts/check_local.sh` 或整套 `vitest`，不要用文件列表挑着跑。** 挑着跑适合"只动了一个组件"的改动；不适合"所有调用方都会走这里"的改动。

这条和上面那条（本地门禁通过只说明本地门禁通过）是一对：一条说本地门禁覆盖不到的需要问 CI，一条说本地门禁自己也要完整地跑。


## 往测试文件末尾追加一个 `describe` 时，别用"去掉最后三个字符"

这个陷阱我踩了三次，三次的表现都一样：`vitest` 报 `no tests` 或 ESLint 报 `Parsing error: '}' expected`。

原因：在一个以 `});` 结尾的文件上做 `text[:-3] + newBlock`，剪掉的是**上一个 describe 的收尾**，于是新块被套进旧块里，少一个闭括号。括号数一数就知道：

```
python3 -c "s=open('文件').read(); print(s.count('{'), s.count('}'))"
```

两个数必须相等。发现不等时，在新增的 `describe(` 之前补一行 `});` 就恢复了——**补在中间而不是末尾**，因为末尾那个 `});` 属于新块。


## 推之前跑完整门禁，而且用脚本而不是记性（2026-09-30）

同一个错误连着犯了两次，两次都是我"只跑了相关的那几个文件"：

1. 把控制器调音接进共享解析路径后，只跑了 SFZ 相关的四个文件——CI 在 `realLibrary.test.ts` 上红了，那条测试读真实库，不在我跑的那几个里。
2. 加了采样器键盘后，只跑了编排相关的测试——CI 在 `desktopSkins.test.ts` 上红了，那条测试检查自动生成的皮肤表，而我的键盘用了一个字面色值，皮肤表需要重新生成。

两次都不微妙，两次都不是"记性"能解决的：**"记得跑整套"这条规则，恰恰在人赶时间时失效。**所以它变成了一条命令：

```
npm run push:dev          # 等价于 bash scripts/push_dev.sh
```

它做三件事，顺序是有意的：跑完整的 `check_local.sh` → 同步镜像 → 提交并推 `dev`。**门禁不过就不推**，所以 `dev` 上不会有本地门禁已经否掉的提交。

推完仍然要问 CI，因为门禁不做的那些（构建体积、浏览器 E2E、探针）判定权在它那里：

```
npm run ci:status
```

三句话放在一起：**本地门禁通过只说明本地门禁通过**；**门禁覆盖不到的由 CI 判**；**跑门禁要跑完整的那一套**。


## 开发推送跑相关的，发版跑全部（2026-09-30）

业主的决定：

> 然后开发过程中 CI/CD 也不一定要全跑，只跑相关的就好，不能拖慢开发迭代速度，发版时候全跑就可以了

按这条把 CI 分成两层：

| 什么时候 | 跑什么 | 为什么 |
| --- | --- | --- |
| 推 `dev`（开发中） | `validate`：类型、lint、单测、构建、bundle budget | 这几项判定"这次改动本身对不对"，几分钟出结果 |
| 推 `main`、开 PR、手动触发 | 以上 + **浏览器矩阵**（桌面与 iPad，每条腿最多 45 分钟） | `main` 就是线上的东西；PR 是"落地之前该被判一次"的地方；手动 = 发版 |
| 发版 | `release.sh` 会调 `npm run ci:full` **并等它出结果**，然后才部署 | "全跑"放在唯一值得它花时间的那一刻 |

```
npm run ci:full            # 触发全量 CI 并等结果，退出码就是 CI 的结论
npm run ci:full -- --no-wait
```

所以本地迭代的节奏是：改 → `npm run push:dev`（它先跑完整本地门禁）→ 看 `npm run ci:status`（几分钟，只有快检查）→ 继续改。发版时才把浏览器矩阵和最重的探针跑一遍。

**不是"发版才检查"**：`validate` 每次都跑，而它覆盖了语法、行为与体积三类回归；被推到发版的是那些**慢**的检查，不是那些**重要**的检查。
