# 离线渲染的评测

TRACK B 要回答的是"44.1 kHz 那 24.4 秒花在哪"，方式是测量，不是重写。

## 已经测到的

| 量 | 值 | 怎么来的 |
| --- | --- | --- |
| 空 `OfflineAudioContext` | 4.8 ms / 4 秒音频（约实时的 0.12%） | 探针的基线档 |
| 展平一步 | 5.5 µs | 探针的展平档 |
| 一首歌在 44.1 kHz 的渲染 | 24.4 s | 探针 |
| 同一首在 8 kHz 单声道 | 1.8 s | 分析通道，13.5× 来自采样率与声道数 |

前两条合起来说明：浏览器图本身的开销可以忽略，24.4 秒花在图的**内容**里；而 2048 小节 × 100 轨 × 16 步的展平本身就是大约 18 秒的纯 JavaScript —— 一百轨的风险既是时间也是内存。

## 轨数成本曲线：怎么测

```
node scripts/measure_lane_curve.mjs --genre=chicago-house            # 1, 4, 16, 64 轨
node scripts/measure_lane_curve.mjs --lanes=16                        # 只测一档
node scripts/probe_arrangement_audio.mjs --only=lane --lanes=16 --json # 底层那一档
```

**每个轨数用一个干净的浏览器进程。** 这不是风格问题，是这台环境下唯一跑得通的方式，理由见下。

曲线测的是**时间与采样到的堆峰值**，而且要说清它测的不是什么：这些轨带一个解析不出任何采样的 `assetId`，所以曲线量的是**规划、轨道构建、主链与渲染**，不是采样解码或播放。堆峰值是采样值（每 10 ms 一次）因此是**下界**，只在 Chromium 里有，而且是**整页**的，不只是渲染那部分。

## 为什么分进程，以及这件事的边界

单次离线渲染就足以让浏览器进程消失：运行以 `[browser] disconnected` 结束，没有 `[crash]`、没有 `[pageerror]`、有时连限幅器的日志都没有——是整个进程没了，不是页面。逐条证据：

- 空闲的浏览器在同一环境里每 30 秒求值一次，活了至少 8 分钟（482 秒），三次开合各自正常求值并正常关闭。所以不是环境在掐长时间运行的东西。
- 同一个探针加不加堆采样**失败方式完全相同**，所以采样不是原因。
- `--only=lane` 跳过其余五个测量块之后仍然失败；把曲线提到所有渲染之前仍然失败——**一次两小节歌曲的渲染就够**。
- 多次运行死在不同的位置：有一次撑过两次渲染，有一次第一次渲染前就死。

**仓库早就知道这个形状。** `manual-verify.yml` 自己写着：159 个曲风的响度重录是分进程跑的，因为"单个浏览器进程在约四十次渲染后耗尽 WASM 预算并自行中止（所以它在笔记本上也从未跑完）"。曲线因此照同样的方式测。

**边界**：这台开发机上拿不到曲线数字本身。它属于 CI 的 `audio` 范围，那里有 `Lane cost curve` 这一步。说"没测到"比编一个数好，而这个项目已经收回两个编出来的数了。
