# `wow`（独立采样引擎）评估 —— 来自 groove 侧的观点

> 被评估文档：`~/music/wow.md`（v1.0，745 行）。评估日期 2026-09-28，基线 groove v2.34.18。
> 评估方法沿用本仓库的规矩：**主张不是证据** —— 每条结论都对着**这个代码库已被测量过的事实**核对。

## 一、这份文档做对的（而且难得）

1. **"一份 Rust 核心，两个宿主"** ✓ —— WASM 给浏览器、napi-rs 给 Node ✓，这是唯一能避免"两份实现漂移"的形状 ✓，也正是本仓库反复用血换来的那条规矩（**一个事实只有一处定义**）✓。
2. **开篇就承认双端不对称** ✓✓ —— §1.2 明说 Node 端 I/O 在 Rust 线程池、浏览器端 I/O 由宿主 Worker 执行 ✓。**大多数架构文档会把这种不对称藏起来** ✗；它写在了第 1.2 节 ✓。
3. **P0 先把 `gs-core` 抽出来，并要求 `synth` 全量测试通过** ✓✓ —— **先还基础设施的债，再盖楼** ✓。这与本仓库的教训完全一致 ✓（"两处算同一件事"是这个代码库最老的缺陷 ✓）。
4. **SLO 自称"可证伪的承诺"** ✓，并配了方法（黄金文件 ✓、sfizz/sforzando 交叉验证 ✓、fuzz ✓、故障注入 ✓）✓ —— 有一个**外部参照物**做 oracle，是 SFZ 解析器能拿到的最强证据 ✓✓。
5. **SAB 不可用时的降级路径写在前面** ✓（Transferable ping-pong + 预取水位加倍 + 阈值调整 ✓），而不是等它在生产里咬人 ✓。
6. **P4 里"互相关零滞后测试"** ✓✓ —— 这正是本仓库刚学会的那种判据 ✓（下面的第四节会说为什么它格外重要 ✓）。

## 二、⚠️ 与这个代码库的实测事实冲突或未交代的地方

### 2.1 `SharedArrayBuffer` 需要 COOP/COEP，而它被写成"配置一行"

文档把跨域隔离当作一个响应头配置 ✓，而它实际是**整个应用的托管约束** ✗✓：一旦开启，任何**跨源资源**都需要 CORP ✓ —— 而 groove 的曲风封面来自 **R2/CDN** ✓、PWA 与分享链接都依赖普通同源加载 ✓ → **这会让封面、字体或任何 CDN 资源静默失效** ✓。

**要求**：把它写成一条**迁移清单**（哪些资源要 CORP ✓、哪些第三方要重新评估 ✓、分享链接的<iframe>嵌入是否还可行 ✓），而不是一句"配置响应头" ✓。

### 2.2 浏览器端"双实例 + SAB 环形队列"是**最冒险**的设计，而文档没有论证它必要

两个 WASM 实例 ✓、一个专用 I/O Worker ✓、一条无锁环形队列 ✓、外加降级路径 ✓ = **四个活动部件** ✓。对一个采样器来说，这个复杂度**可能是对的**（磁盘流式 + 实时线程确实需要解耦 ✓），但文档没有给出**它换来了什么、以及不这么做会损失什么** ✗ —— 按本仓库的规矩 ✓：**要么给出测量，要么说明这是为将来的规模预留** ✓。

**而本仓库刚测过一件相关的事** ✓✓：它自己的**离线渲染是有状态、且状态跨越整首曲子**的 ✗（分块实验的结论 ✓：差异贯穿整块 ✓）。**环形队列是一条新的状态边界** ✓ → 它会以同样的方式咬人 ✓ → 所以它需要**同一种判据**：不是"无锁所以安全" ✓，而是**在环形队列被喂满/喂空/交错时，输出与直连渲染逐样本一致** ✓✓。

### 2.3 "Node 端离线渲染"——**它到底渲染谁**？

⭐ 这是这份文档**最重要的一处含糊** ✗✓，也是它**最可能被低估的价值** ✓。

- 若 `wow` 的原生路径只渲染**它自己拥有的采样声部** ✓，那么 groove 的**整曲渲染仍然需要浏览器** ✗（因为合成器声部、效果器、母带链都在浏览器侧 ✓）→ 本工作流刚刚花掉四轮测出的那个结论依然成立 ✓（`startRendering()` 无回调 ✓、无进度 ✓、分块不等价 ✓）。
- 若它的原生路径能被用作**整曲渲染后端** ✓✓，那它就不只是一个采样器 ✓ —— **它是 groove 路线图里 Phase 0 的 "RenderTarget 抽象"** ✓✓（那条至今**未做** ✓），并且**一举解掉**当前唯一剩下的两个 P0 之一 ✓。

**要求**：文档必须明确回答"原生渲染的边界在哪里" ✓，并**如果它想承担整曲渲染** ✓，就必须把那部分（效果链、母带、多轨归约、确定性哈希 ✓）**写进范围** ✓ —— 否则它交付之后，宿主仍然要在浏览器里渲染 ✓，而"Node 端效率低下"这个动机**没有被解决** ✗。

### 2.4 成本落在**别人的仓库**上

P0 是"剥离 `gs-core`" ✓ —— 也就是**对一个能工作的项目做重构** ✓。文档只用一条验收线覆盖它（`synth` 全量测试通过 ✓），但没有说**若 `synth` 行为改变，谁来决定接受还是回滚** ✗ ✓。建议补一条：**重构后的 `synth` 输出与重构前逐样本一致**（它自己的确定性测试应当能给出这个 ✓）✓。

## 三、范围与优先级：与 groove 当下**已有的东西**对照

| 能力 | groove 今天 | `wow` 会给 |
|---|---|---|
| 采样播放（按小节起播 ✓） | ⭐ **本次工作流已建成** ✓（计划器 ✓ / 事件→秒 ✓ / 单次解码与失败不缓存 ✓ / 调度器 ✓ / 浏览器适配器 ✓；**13 条判据** ✓） | 更专业（SFZ ✓、流式 ✓、round robin ✓、voice stealing ✓） |
| 路径的延迟 | ⭐ **已实测为 0** ✓（`start(when)` 规范精确起播 ✓） | 需要**重新实测**（多了一层解码/环/插值 ✓） |
| 真实乐器（SFZ 库） | **没有** ✗ | ⭐ **这是它真正的价值** ✓ |
| 原生/无头渲染 | **没有** ✗（依赖 Chromium ✓） | 若有（见 2.3）→ ⭐ **价值更大** ✓ |

⭐ **结论**：`wow` 的价值**不在"采样播放"**（那件事本工作流已经用 13 条判据做完了 ✓），而在 **SFZ/真实乐器** ✓ 与（可能）**原生整曲渲染** ✓。文档应当按这个重新定位 ✓。

## 四、值得先做的一件事（在我看来的最小可信步）

按本仓库自己的规矩 ✓（**先有第二个消费者，再抽抽象** ✓），以及它自己为 `gs-core` 设计的路径 ✓（**从一个能工作的项目里抽出来** ✓）：

1. **先在现有引擎里做 SFZ 的一个子集** ✓（不新建仓库 ✗）：解析 ✓ + 分区映射 ✓ + 一个真实乐器 ✓，用**已有的**播放与调度路径 ✓（本工作流的 `planAudioLaneEvents` ✓ / `load` ✓ / `sink` ✓ 三个注入点已经等在那里 ✓✓）；
2. **判据**：与 **sfizz** 对同一个 `.sfz` 的输出**逐样本在 epsilon 内** ✓✓（文档自己提的交叉验证 ✓ —— 提前到第一步 ✓）；
3. 只有**当第二个宿主真的要用**时 ✓（`synth` 或 Node 渲染 ✓），才把它抽成 `wow` ✓ —— 那时 `gs-core` 的边界已经被**真实需求**画出来了 ✓，而不是被预测画出来 ✓。

⚠️ 这样做的代价是：**短期内拿不到原生离线渲染** ✓。收益是：**不会用 36 周去建一个还没有第二个消费者的抽象** ✓，而且**第一步就能给作曲家一个真实乐器** ✓。

## 六、一句话结论

**方向对、工程素养高、优先级错位**：`wow` 把"采样播放"当成要解决的问题 ✓，而它在 groove 里**已经解决了** ✓；真正缺的是 **SFZ 真实乐器** ✓ 与 **原生整曲渲染** ✓。建议**先按第四节的"最小可信步"在现有引擎里验证 SFZ** ✓，**同时**要求文档回答 2.1 与 2.3 两个问题 ✓ —— 然后才决定是否开新仓库 ✓。
